# RF-02 — Validación de solicitudes

## Descripción

El módulo `validator` implementa la capa de validación de entrada de Hermes. Actúa como guardián en el punto de entrada: toda solicitud pasa por él antes de crear un Job o consultar el historial. Su responsabilidad es rechazar entradas vacías, mal formadas o no autorizadas con un mensaje útil que indique qué se esperaba.

La validación se separa en dos capas intencionalmente. La existencia de los argumentos (`argc`) se verifica en `main.cpp` para proteger la memoria, mientras que el contenido de los argumentos (`argv`) se delega a `validator` para proteger la lógica de negocio. Esta división evita tanto accesos fuera de rango como persistencia de datos inválidos.

El módulo es transversal y sin estado: no conoce el JSON ni los procesos, solo reglas de texto. Por eso puede ser reutilizado por `job`, `filter` y, en el futuro, por `network` sin duplicar lógica.

---

## Objetivo

La meta técnica exacta de este RF es centralizar el rechazo temprano de solicitudes inválidas con códigos tipados y mensajes accionables, eliminando los crasheos por conversión numérica directa.

> El sistema deberá validar la solicitud y rechazar entradas vacías, mal formadas o no autorizadas con un mensaje útil.

Consideraciones actuales:
- Hace: valida comando (`job`, `filter`, `--version`), programa no vacío, tipo de filtro (`id`, `status`, `programa`), ID numérico estricto (`> 0`, sin basura parcial como `12x`) y estado contra la lista blanca (`QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELED`).
- Hace: encapsula `std::stoul` con `try/catch` (`invalid_argument`, `out_of_range`) y verificación de `pos` para que `main.cpp` nunca convierta a ciegas.
- NO hace: validación de existencia en disco (si el ID es válido pero no existe, responde `filter`, no `validator`).
- NO hace: saneamiento de programas contra inyección o verificación de que el programa exista en `PATH`. Eso pertenece a RF-04 (ejecución).
- NO hace: normalización (minúsculas, recorte de espacios). La comparación es exacta y sensible a mayúsculas.

## Estructura del módulo

```text
hermes/
├── include/
│   └── validator.h
├── src/
│   ├── main.cpp
│   └── validator/
│       └── validator.cpp
└── Makefile
```

| Archivo / directorio | Responsabilidad |
| -------------------- | --------------- |
| `include/validator.h` | Contrato: `enum class CodigoValidacion`, `struct ResultadoValidacion` y prototipos de validación |
| `src/validator/validator.cpp` | Lógica de validación: listas blancas, `stoul` protegido y mensajes útiles |
| `src/main.cpp` | Guardián de entrada: invoca al validador antes de delegar a `job` o `filter` |
| `Makefile` | Descubre `validator.cpp` vía `find src -name '*.cpp'` sin edición manual |

## Definición de los estados

Este RF introduce su propio `enum class` de resultado, independiente de `Status`:

```cpp
enum class CodigoValidacion {
    OK,
    VACIO,
    MALFORMADO,
    NO_AUTORIZADO
};
```

| Valor | Significado en el ciclo de vida de la solicitud |
| ----- | ----------------------------------------------- |
| `OK` | La entrada es aceptable. El flujo continúa hacia `crearJob` o `filtrarPor*`. `mensaje` va vacío. |
| `VACIO` | Falta contenido (`""`). Ejemplo: `hermes job ""`. Se rechaza antes de tocar el JSON. |
| `MALFORMADO` | Contenido con forma incorrecta. Ejemplo: `id` con `"abc"`, `"12x"`, `"0"` o desbordamiento. Se rechaza sin crashear. |
| `NO_AUTORIZADO` | Contenido bien formado pero fuera de la lista blanca. Ejemplo: comando `foo`, filtro `bar`, estado `running` en minúsculas. El mensaje lista los valores permitidos. |

El `struct` que transporta el veredicto es:

```cpp
struct ResultadoValidacion {
    bool esValido;
    CodigoValidacion codigo;
    string mensaje;
};
```

Se diseñó así porque quien llama solo necesita `if (!r.esValido)`: ya tiene el código para lógica y el mensaje listo para `error()` sin adivinar.

## Implementación de `.h`

**1. Propósito del archivo.**

`validator.h` es el contrato transversal de RF-02. Declara qué se puede validar sin revelar cómo. Permite que `main.cpp` lo incluya con `#include "validator.h"` gracias al flag `-Iinclude`.

**2. Dependencias incluidas.**

```cpp
#include <string>
```

Solo `string`. No depende de `job.h`, `filter.h` ni `nlohmann/json`: a propósito, para mantenerlo sin estado y sin acoplamiento a persistencia.

**3. Estructuras de datos.**

`CodigoValidacion` (arriba) evita enteros mágicos y `ResultadoValidacion` empaqueta el veredicto completo. Ambos usan tipos por valor pequeños (`bool`, `enum`, `string`) sin manejo manual de memoria.

**4. Prototipos de funciones clave.**

```cpp
ResultadoValidacion validarComando(const string& comando);
ResultadoValidacion validarPrograma(const string& programa);
ResultadoValidacion validarTipoFiltro(const string& tipoFiltro);
ResultadoValidacion validarIdTexto(const string& textoId);
ResultadoValidacion validarStatusTexto(const string& status);
```

Todas reciben `const string&` para evitar copias. `validarIdTexto` recibe el texto crudo de `argv` (no un número) porque el peligro está en convertir. `validarPrograma` se reutiliza para `hermes job <programa>` y para `hermes filter programa <valor>` porque la regla es idéntica: texto no vacío.

## Implementación de `.cpp`

El archivo `src/validator/validator.cpp` incluye:

```cpp
#include "validator.h"
#include <stdexcept>
```

`<stdexcept>` es necesario para capturar `std::invalid_argument` y `std::out_of_range` que lanza `std::stoul`. Sin él, la conversión numérica quedaría sin red de seguridad.

### Validación por lista blanca

`validarComando`, `validarTipoFiltro` y `validarStatusTexto` siguen el mismo patrón: vacío primero, lista blanca después, rechazo con mensaje que lista lo permitido.

```cpp
if (comando.empty()) {
    return {false, CodigoValidacion::VACIO, "Comando vacio. Comandos validos: job, filter, --version"};
}
if (comando == "job" || comando == "filter" || comando == "--version") {
    return {true, CodigoValidacion::OK, ""};
}
return {false, CodigoValidacion::NO_AUTORIZADO, "Comando no reconocido: " + comando + ". Comandos validos: job, filter, --version"};
```

Se eligió comparación exacta (sensible a mayúsculas) para mantener coherencia con `statusToString`, que persiste `QUEUED` en mayúsculas. Normalizar se descartó en esta etapa para no ocultar errores del usuario.

### Validación numérica estricta con `pos`

`validarIdTexto` es la función crítica porque reemplaza el antiguo `std::stoul(argv[3])` directo que crasheaba con `"abc"`:

```cpp
size_t pos = 0;
unsigned long valor = std::stoul(textoId, &pos);
if (pos != textoId.size()) {
    return {false, CodigoValidacion::MALFORMADO, "ID mal formado: " + textoId + ". Debe ser un numero entero positivo."};
}
if (valor == 0) {
    return {false, CodigoValidacion::MALFORMADO, "ID mal formado: debe ser mayor a 0."};
}
```

`stoul(texto, &pos)` es permisivo por diseño: convierte `"12x"` en `12` con `pos = 2`. Sin el chequeo `pos != size`, ese caso se aceptaría como `12` (falso positivo). Con el chequeo se exige consumo total. Los casos de basura total (`"abc"`) lanzan `invalid_argument` y los de desbordamiento (`"99999999999999999999"`) lanzan `out_of_range`; ambos se capturan y se devuelven como `MALFORMADO` sin propagar la excepción.

El valor `0` se rechaza porque los IDs generados por `crearJob` empiezan en `1`.

## Integración con `main.cpp`, `job` y `filter`

`main.cpp` es el único punto por donde pasan todos los comandos, por eso la integración se hizo allí y no dentro de `job.cpp` ni `filter.cpp`. Cada rama sigue el patrón guardián:

```cpp
ResultadoValidacion ri = validarIdTexto(argv[3]);
if (!ri.esValido) {
    error(ri.mensaje);
    return 1;
}
unsigned int id = static_cast<unsigned int>(std::stoul(argv[3]));
filtrarPorId(id);
```

El flujo completo es:

1. `validarComando(argv[1])` antes de cualquier despacho.
2. En rama `job`: verificación de existencia `if (argc < 3)` (memoria) y luego `validarPrograma(argv[2])` (negocio). Solo entonces `crearJob`.
3. En rama `filter`: verificación de existencia `if (argc < 4)` (memoria), luego `validarTipoFiltro(argv[2])` y según el subtipo `validarIdTexto`, `validarStatusTexto` o `validarPrograma` sobre `argv[3]`. Solo entonces `filtrarPorId/Status/Programa`.

La distinción `argc` (existencia) vs `validator` (contenido) es intencional: el validador nunca se llama con un `argv` inexistente.

## Integración con RF-01

Este requisito amplía RF-01 (envío de comando y generación de ID) sin modificar su persistencia. RF-01 definió `crearJob` y `data/jobs.json`; RF-02 agrega la puerta de entrada que impide que RF-01 persista programas vacíos. También protege a RF-09 (`filter`) y RF-06 (`status`): el filtro por ID ya no crashea y el filtro por estado solo acepta los cinco valores del `enum class Status`.

## Ejemplo de funcionamiento

**1. Entrada mal formada (rechazo sin crash):**

```bash
./hermes filter id 12x
```

**2. Salida en consola:**

```text
ID mal formado: 12x. Debe ser un numero entero positivo.
```

El programa termina con código `1` y nunca llama a `filtrarPorId`.

**3. Entrada no autorizada:**

```bash
./hermes filter status running
```

```text
Estado no reconocido: running. Estados validos: QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELED
```

**4. Entrada válida (flujo completo):**

```bash
./hermes job sleep 5
./hermes filter id 1
```

```text
job ID: 1
Job ID: 1
Programa: sleep
Estado: QUEUED
Argumentos: 5
```

El archivo `data/jobs.json` solo se modifica en el caso válido:

```json
[
    {
        "job_id": 1,
        "programa": "sleep",
        "argumentos": [
            "5"
        ],
        "status": "QUEUED"
    }
]
```

Los tres casos inválidos no dejan rastro en disco: el rechazo temprano garantiza ausencia de efectos laterales.
