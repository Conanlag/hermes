# RF-12 — Persistencia de metadatos y resultados

## Descripción

RF-12 establece que el sistema deberá conservar metadatos y resultados mínimos después de reiniciar el servicio. Hermes satisface el requisito manteniendo los Jobs en `jobs.json`, dentro de `$HOME/.local/share/hermes/data/`, y actualizando ese archivo mediante la capa de almacenamiento compartida.

La persistencia incluye los datos necesarios para identificar un Job, conocer su solicitud y consultar su último estado y resultado. Si el servicio se detiene mientras el proceso estaba activo, Hermes no inventa un resultado de ejecución: el Job se conserva con estado `INTERRUPTED` y código de salida `-1`, mientras que los trabajos que aún estaban `QUEUED` permanecen pendientes.

---

## Objetivo

> RF-12 — El sistema deberá conservar metadatos y resultados mínimos después de reiniciar el servicio.

Al iniciar Hermes nuevamente, las consultas deben poder recuperar los Jobs ya aceptados y mostrar sus metadatos y el resultado que se alcanzó a persistir. Las actualizaciones del archivo deben estar sincronizadas entre procesos y ser atómicas y durables, para no perder el historial por una escritura parcial o una interrupción.

```text

│   ├── job.h
│   ├── status.h

    ├── job/

    │   └── scheduler.cpp
    ├── recovery/
    │   └── recovery.cpp
    ├── filter/
    │   └── filter.cpp
    └── main.cpp
```

| Archivo | Responsabilidad |
|---|---|
| `include/data_paths.h` | Resuelve la ruta persistente y crea los archivos de datos que faltan. |
| `include/job.h` / `src/job/job.cpp` | Define el modelo del Job, registra solicitudes y reconstruye registros desde el almacenamiento. |
| `include/storage.h` / `src/storage/storage.cpp` | Serializa el acceso con `jobs.lock`, lee el respaldo cuando hace falta y persiste modificaciones de manera atómica. |
| `include/status.h` / `src/status/status.cpp` | Convierte el estado entre el enum de C++ y su representación persistida. |
| `src/scheduler/scheduler.cpp` | Persiste reservas, PID, resultados de procesos y estados de interrupción. |
| `src/recovery/recovery.cpp` | Reconcilia Jobs que quedaron en `RUNNING` cuando el supervisor anterior dejó de existir. |
| `src/filter/filter.cpp` | Consulta los Jobs a través de `leerJobsSeguros()`. |

## Definición de los estados

Cada registro persiste un estado textual para que pueda consultarse después de reiniciar el servicio:

| Estado | Significado persistido |
|---|---|
| `QUEUED` | Job aceptado y pendiente de reserva por un worker. |
| `RUNNING` | Job reservado y supervisado por el scheduler. |
| `SUCCEEDED` | El proceso terminó correctamente. |
| `FAILED` | El proceso terminó con error o no pudo iniciarse. |
| `CANCELED` | La solicitud de cancelación terminó correctamente. |
| `INTERRUPTED` | Hermes dejó de supervisar el proceso y no afirma un resultado de ejecución que no pudo verificar. |

Un estado desconocido se maneja de forma conservadora como `INTERRUPTED`; no se transforma en `QUEUED`, porque eso podría reejecutar un trabajo cuyo estado no se entiende.

## Implementación de `.h`

`Job` expone los datos que la aplicación reconstruye al consultar un registro: `job_id`, `pid`, `programa`, `argumentos`, `status`, marcas de tiempo, `codigoSalida`, `mensajeError` y, si existe, `request_id`.

La capa de almacenamiento expone operaciones compartidas:

```cpp
json leerJobsSeguros();
bool modificarJobsSeguros(
    const std::function<bool(json&)>& funcion
);
void limpiarTemporalesDeJobs();
```

Las lecturas y modificaciones usan `jobs.lock`; `modificarJobsSeguros()` mantiene el ciclo lectura-modificación-escritura dentro de la misma sección protegida.

## Implementación de `.cpp`

### Metadatos persistidos

Al crear un Job, Hermes registra como mínimo:

| Campo | Uso |
|---|---|
| `job_id` | Identificador persistente y creciente. |
| `programa` y `argumentos` | Solicitud que Hermes ejecutará. |
| `status` | Estado del ciclo de vida. |
| `pid` | PID del proceso; comienza en `0` y se persiste cuando el proceso está creado. |
| `tiempo_recepcion`, `tiempo_inicio`, `tiempo_terminacion` | Marcas de tiempo disponibles para consultar el ciclo de vida. |
| `codigo_salida` | Código observado o `-1` cuando aún no hay resultado verificable. |
| `cancel_requested` | Indica si se solicitó cancelar un Job en ejecución. |
| `mensaje_error` | Diagnóstico cuando una ejecución falla o se interrumpe. |
| `request_id` | Identificador opcional para correlación e idempotencia. |

Los campos de identidad de proceso y recuperación (`boot_id`, `pid_inicio`, `sid`, `motivo`, `proceso_terminado` y `recuperado_en`) son aditivos y permiten verificar las transiciones tras una caída. El lector conserva compatibilidad con registros anteriores mediante valores predeterminados para campos ausentes.

### Escritura y lectura

`guardarAtomico()` en `storage.cpp` implementa el protocolo de persistencia:

1. Crea un temporal único `jobs.json.tmp.<pid>.<contador>` con `O_CREAT | O_EXCL | O_CLOEXEC`.
2. Escribe todos los bytes, repitiendo ante `EINTR`.
3. Ejecuta `fsync()` sobre el temporal.
4. Actualiza `jobs.json.bak` mediante `link()` solo si el archivo principal contiene un arreglo JSON válido.
5. Sustituye `jobs.json` con `rename()` y sincroniza el directorio.
6. Ante un fallo, cierra descriptores y elimina el temporal cuando corresponde.

La lectura intenta `jobs.json` y usa `jobs.json.bak` si el principal no puede parsearse. Si restaura desde el respaldo, registra la recuperación y repara el archivo principal. Si no hay una copia válida, reporta un error en lugar de devolver silenciosamente un historial vacío.

Las consultas por ID, estado y programa usan la capa segura de almacenamiento; no mantienen parsers alternativos que lean el archivo por fuera de `jobs.lock`.

### Reinicio del servicio

Al iniciar el scheduler, Hermes comprueba `scheduler.lock`. Si no existe un daemon activo, recupera los registros antes de iniciar uno nuevo: los `RUNNING` que ya no tienen supervisor se convierten en `INTERRUPTED`; los `QUEUED` y los estados terminales se conservan. Los Jobs interrumpidos no se ejecutan automáticamente.

El apagado ordenado mediante `hermes clean scheduler` registra como `INTERRUPTED` los Jobs que estaban activos y deja intactos los que seguían en cola. Así el reinicio conserva tanto el historial como la distinción entre resultado observado y ejecución interrumpida.

## Integración con otros módulos

- **RF-13 (recuperación tras reinicio):** usa metadatos persistidos para reconciliar Jobs `RUNNING` y verificar la identidad del proceso antes de señalizarlo.
- **RF-06 (estados):** define la representación textual y las transiciones que se consultan después de reiniciar.
- **RF-08 (consulta por ID) y RF-09 (filtros):** recuperan registros mediante el almacenamiento seguro.
- **RF-10 (cancelación):** persiste la solicitud y el resultado de cancelación.
- **RF-14 (bitácora):** registra eventos asociados a Jobs sin sustituir el registro persistente en `jobs.json`.
- **RNF-11 (escritura atómica):** proporciona durabilidad, respaldo y restauración frente a escrituras interrumpidas.

La decisión original de almacenar los Jobs en JSON se registra en [ADR-005](../../desicions/ADR-005-Persistencia.md).

## Ejemplo de funcionamiento

Una solicitud se guarda al aceptarse y puede consultarse de nuevo tras iniciar Hermes:

```bash
hermes job sleep 30
```

```text
job ID: 7
PID: 12345
```

Si se detiene el scheduler ordenadamente mientras el Job sigue activo:

```bash
hermes clean scheduler
hermes filter id 7
```

El registro permanece en `jobs.json`; el resultado indica que Hermes interrumpió la supervisión, en lugar de afirmar un éxito o fallo no observado:

```text
Job ID: 7
Programa: sleep
Estado: INTERRUPTED
Codigo de salida: -1
```

Los Jobs que estaban en `QUEUED` también permanecen en el archivo y pueden ser retomados por un scheduler posterior.
