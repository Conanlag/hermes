# RF-06 — Estados de los Jobs

## Descripción

Hermes utiliza un conjunto definido de estados para representar el ciclo de vida de cada Job:

```text
QUEUED
RUNNING
SUCCEEDED
FAILED
CANCELED
INTERRUPTED
```

Los estados se encuentran definidos mediante:

```cpp
enum class Status {
    QUEUED,
    RUNNING,
    SUCCEEDED,
    FAILED,
    CANCELED,
    INTERRUPTED
};
```

`INTERRUPTED` se añadió en el RF-13: representa un Job que Hermes dejó de supervisar sin conocer su resultado real (apagado ordenado, caída del demonio o estado persistido ininteligible). Es terminal y nunca se reejecuta automáticamente.

La implementación se encuentra separada del módulo `job`, mediante:

```text
include/status.h
src/status/status.cpp
```

---

# Objetivo

RF-06 permite representar el estado real de un Job durante su ciclo de vida.

Los estados permiten distinguir entre:

* Jobs creados y pendientes.
* Jobs actualmente ejecutándose.
* Jobs terminados correctamente.
* Jobs terminados con errores.
* Jobs cancelados.
* Jobs interrumpidos por una caída o un apagado del supervisor.

---

# Estado `QUEUED`

`QUEUED` representa el estado inicial de un Job.

Cuando Hermes crea un Job, su estado inicial es:

```cpp
job.status = Status::QUEUED;
```

No se recibe el estado como parámetro de `crearJob()`.

Esto evita que el usuario pueda crear directamente un Job con un estado arbitrario.

---

# Estado `RUNNING`

Cuando el proceso asociado comienza su ejecución, Hermes actualiza el estado:

```text
QUEUED → RUNNING
```

Este estado significa que existe un proceso asociado al Job y que dicho proceso continúa ejecutándose.

---

# Estado `SUCCEEDED`

Cuando el proceso termina correctamente, Hermes registra:

```text
RUNNING → SUCCEEDED
```

Normalmente corresponde a un código de salida:

```text
0
```

Por ejemplo:

```text
Programa: echo
Estado: SUCCEEDED
Código de salida: 0
```

---

# Estado `FAILED`

Cuando el proceso termina indicando un error, Hermes registra:

```text
RUNNING → FAILED
```

El resultado de la ejecución se obtiene mediante la supervisión del proceso.

Por ejemplo, si `execvp()` no puede ejecutar el programa solicitado, el proceso puede terminar indicando un código de error.

---

# Estado `CANCELED`

Cuando el usuario solicita:

```bash
hermes cancel <id>
```

Hermes localiza el proceso asociado al Job y solicita su terminación.

El ciclo correspondiente es:

```text
RUNNING
   │
   │ hermes cancel <id>
   ▼
CANCELED
```

La implementación utiliza el PID asociado al Job para realizar la terminación del proceso.

---

# Estado `INTERRUPTED`

`INTERRUPTED` es un estado **terminal** que indica que Hermes dejó de supervisar el Job y no puede afirmar si su programa terminó bien, mal o sigue vivo. Se añadió con el RF-13 (recuperación después de reinicio) y se escribe en dos escenarios:

1. **Apagado ordenado (`SIGTERM`/`SIGINT` al demonio):** el coordinador de apagado termina los grupos de procesos activos y persiste la fila con `motivo=apagado`.
2. **Recuperación al arrancar:** si la fila quedó `RUNNING` porque el demonio murió (caída, `SIGKILL`, corte de energía), el proceso CLI que demuestra que no hay daemon vivo reconcilia la fila con el `motivo` que corresponda (`caida`, `sin_pid`, `sin_identidad`, `pid_reutilizado` o `estado_desconocido`).

El campo `motivo` es aditivo, solo tiene sentido para este estado y forma parte de la evidencia persistida:

```text
apagado | caida | sin_pid | sin_identidad | pid_reutilizado | estado_desconocido
```

Además de `motivo`, la fila conserva `proceso_terminado` (si Hermes pudo confirmar que el proceso ya no existe), `codigo_salida=-1` y un `mensaje_error` legible.

Reglas de comportamiento:

* Nunca se reejecuta automáticamente: el resultado real es desconocido y repetir el efecto sería peor que informarlo.
* No se asigna `CANCELED`: el Job no fue cancelado por el usuario. `cancel_requested` se conserva como evidencia si existía.
* Un `status` desconocido en `jobs.json` se trata como `INTERRUPTED` con `motivo=estado_desconocido` (fail-closed): nunca se reporta como pendiente ni se asume `QUEUED`.
* Las transiciones de la recuperación son idempotentes: una fila ya terminal (`SUCCEEDED`, `FAILED`, `CANCELED` o `INTERRUPTED`) no se modifica.

---

# Ciclo de vida

El ciclo general es:

```text
             crear Job
                 │
                 ▼
              QUEUED
                 │
                 ▼
              RUNNING
             /    |    \        \
            /     |     \        \
           ▼      ▼      ▼        ▼
     SUCCEEDED  FAILED  CANCELED  INTERRUPTED
```

Las transiciones principales son:

```text
QUEUED → RUNNING

RUNNING → SUCCEEDED

RUNNING → FAILED

RUNNING → CANCELED

RUNNING → INTERRUPTED   (apagado ordenado o recuperación tras caída)

QUEUED  → INTERRUPTED   (estado persistido ininteligible)
```

La transición a `INTERRUPTED` no la decide el worker que ejecutó el Job: en el apagado la escribe el coordinador del demonio, y en la caída la escribe la recuperación del siguiente comando. Así hay un único escritor y nunca se pisa una fila terminal.

# Implementación de `status.h`

```cpp
#ifndef STATUS_H
#define STATUS_H

#include <string>

using std::string;

enum class Status {
    QUEUED,
    RUNNING,
    SUCCEEDED,
    FAILED,
    CANCELED,
    INTERRUPTED
};

string statusToString(Status status);

// Convierte texto persistido a Status. Un valor desconocido NO se asume
// QUEUED: se trata como INTERRUPTED para fallar en cerrado (RNF-31).
Status statusDesdeTexto(const string& texto);

// Indica si el texto corresponde a un estado conocido del dominio.
bool statusEsTextoConocido(const string& texto);

#endif
```

El uso de `enum class` permite trabajar con estados definidos por el programa en lugar de utilizar cadenas directamente.

Por ejemplo:

```cpp
job.status = Status::RUNNING;
```

---

# Implementación de `status.cpp`

La conversión a texto se realiza mediante:

```cpp
string statusToString(Status status) {

    switch (status) {

    case Status::QUEUED:
        return "QUEUED";

    case Status::RUNNING:
        return "RUNNING";

    case Status::SUCCEEDED:
        return "SUCCEEDED";

    case Status::FAILED:
        return "FAILED";

    case Status::CANCELED:
        return "CANCELED";

    case Status::INTERRUPTED:
        return "INTERRUPTED";
    }

    return "INTERRUPTED";
}
```

El valor por defecto también es `INTERRUPTED`: si el `switch` recibiera un valor fuera del dominio, reportarlo como `QUEUED` lo haría parecer pendiente y podría reejecutarse. Es la misma política fail-closed de `statusDesdeTexto()`.

Esto permite convertir:

```cpp
Status::RUNNING
```

en:

```text
RUNNING
```

para mostrarlo o almacenarlo en JSON.

# Integración con `Job`

Actualmente un Job contiene:

```cpp
struct Job {

    unsigned int job_id;

    int pid;

    string programa;

    vector<string> argumentos;

    Status status;

    int codigoSalida;

};
```

La información representa:

```text
Job
├── job_id
├── pid
├── programa
├── argumentos
├── status
└── codigoSalida
```

---

# Actualización del estado

El estado se modifica conforme al resultado de la ejecución.

El flujo general es:

```text
crearJob()
    │
    ▼
QUEUED
    │
    ▼
crear proceso
    │
    ▼
RUNNING
    │
    ▼
esperar proceso
    │
    ├── terminó correctamente
    │       │
    │       ▼
    │   SUCCEEDED
    │
    ├── terminó con error
    │       │
    │       ▼
    │    FAILED
    │
    ├── fue cancelado
    │       │
    │       ▼
    │   CANCELED
    │
    └── el supervisor se apagó o murió antes de recogerlo
            │
            ▼
        INTERRUPTED
```

La supervisión se realiza utilizando las funciones del módulo `process`.

---

# Supervisión mediante `waitpid()`

El módulo de procesos proporciona la funcionalidad necesaria para esperar la terminación de un proceso.

Conceptualmente:

```cpp
esperarProceso(pid, codigoSalida);
```

utiliza `waitpid()` internamente.

Esto permite que `job.cpp` no tenga que implementar directamente los detalles de la llamada al sistema.

La separación queda de la siguiente forma:

```text
job.cpp
   │
   └── solicita supervisión
            │
            ▼
       process.cpp
            │
            └── waitpid()
```

---

# Código de salida

El código obtenido del proceso se almacena en:

```cpp
codigoSalida
```

Esto permite conservar información adicional al estado.

Ejemplo:

```text
Estado: SUCCEEDED
Código de salida: 0
```

o:

```text
Estado: FAILED
Código de salida: 127
```

---

# Persistencia del estado

El estado forma parte de la información almacenada físicamente en:

```text
$HOME/.local/share/hermes/data/jobs.json
```

En el repositorio se puede acceder al mismo archivo mediante el enlace simbólico `src/hermes/data/jobs.json`.

Ejemplo:

```json
{
    "job_id": 7,
    "pid": 5053,
    "programa": "sleep",
    "argumentos": [
        "120"
    ],
    "status": "RUNNING",
    "codigoSalida": 0
}
```

Cuando el proceso termina, Hermes actualiza la información correspondiente al Job.

---

# Cancelación

El mecanismo de cancelación utiliza el PID almacenado en el Job.

El flujo es:

```text
hermes cancel 7
       │
       ▼
buscar Job 7
       │
       ▼
obtener PID
       │
       ▼
terminar proceso
       │
       ▼
CANCELED
```

Esto permite relacionar la operación de cancelación de Hermes con el proceso real administrado por Linux.

---

# Integración con RF-01

RF-01 proporciona la creación y ejecución del proceso.

RF-06 agrega el seguimiento de su ciclo de vida.

Por lo tanto:

```text
RF-01
   │
   ├── crea Job
   ├── crea proceso
   └── obtiene PID
            │
            ▼
          RF-06
            │
            ├── QUEUED
            ├── RUNNING
            ├── SUCCEEDED
            ├── FAILED
            ├── CANCELED
            └── INTERRUPTED
```

# Alcance actual

RF-06 actualmente contempla:

* Seis estados definidos.
* `enum class Status`.
* Estado inicial `QUEUED`.
* Transición a `RUNNING`.
* Detección de terminación del proceso.
* Transición a `SUCCEEDED`.
* Transición a `FAILED`.
* Cancelación de Jobs en ejecución.
* Estado `CANCELED`.
* Estado terminal `INTERRUPTED` con `motivo` (`apagado`, `caida`, `sin_pid`, `sin_identidad`, `pid_reutilizado`, `estado_desconocido`), `proceso_terminado` y `mensaje_error`.
* Fail-closed: un estado persistido desconocido se trata como `INTERRUPTED`, nunca como `QUEUED`.
* Código de salida.
* Persistencia del estado en `jobs.json`.
* Separación del módulo de estados.
