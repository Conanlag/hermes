# TC-036: Una operación rechazada no altera el estado aunque el cliente corte

**Requisitos cubiertos:** RF-28
**Métodos de verificación:** Prueba
**Nivel de prueba:** Funcional y robustez

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Verificar que una operación rechazada por estado no cancelable no modifica `jobs.json` y queda documentada como `RECHAZADA` con su código de error cuando el cliente corta antes de leer la respuesta.
* **Precondiciones:** Linux o WSL con Bash y Python 3; Hermes compilado; `HOME` temporal aislado; puerto `45831` libre.
* **Entorno y configuración:** `config.json` propio de la prueba con `puerto: 45831`; `network.json` que autoriza a `PC-B` desde `127.0.0.1`; servidor lanzado por el script.
* **Datos de entrada:** Un `submit` de `true` confirmado y llevado a estado terminal, seguido de un `cancel` sobre ese mismo `job_id` con `request_id: tc036-rechazo` y `RST` inmediato tras enviar.
* **Pasos reproducibles:**
  1. Compilar con `make -C src/hermes hermes`.
  2. Ejecutar `bash verif/scripts/TC-036.sh`.
  3. Revisar el código de salida y `verif/results/results_TC-036.md`.
* **Resultado esperado:** El `sha256` de `jobs.json` es idéntico antes y después del rechazo; el evento `Solicitud interrumpida` declara `resultado: RECHAZADA`, `error: NOT_CANCELABLE`, la operación `cancel` y el `job_id` afectado, nunca `ACEPTADA`; el Job original conserva su estado terminal y el servicio responde un `ping` posterior.

#### 2. Fase de Ejecución (Resultados empíricos)
* **Resultado observado:** Ejecución del 2026-11-19 en WSL Ubuntu con código `0`. `jobs.json` conservó el mismo `sha256`; la bitácora registró `Solicitud interrumpida` con `resultado: RECHAZADA`, `error: NOT_CANCELABLE`, `motivo: ERROR_SOCKET`, `operacion: cancel`, `request_id: tc036-rechazo`, `job_id: 1` y `bytes_recibidos: 94`; el Job base siguió en estado terminal y el `ping` posterior respondió correctamente.
* **Artefactos de evidencia:** `verif/scripts/TC-036.sh`; `verif/results/results_TC-036.md`.
