# RF-11 — Manejo separado de stdout y stderr

## Descripción

RF-11 establece la separación entre los canales estándar utilizados por Hermes y por los procesos ejecutados.

Linux proporciona principalmente:

```text
stdin  → descriptor 0
stdout → descriptor 1
stderr → descriptor 2
```

Hermes utiliza:

```text
stdout → información normal
stderr → errores y advertencias
```

Además, los procesos ejecutados por Hermes conservan sus propios canales estándar.

Esto significa que un mensaje producido por un programa hijo no debe confundirse automáticamente con un error generado por Hermes.

---

# Objetivo

RF-11 busca proporcionar una separación clara entre:

```text
stdout
```

y:

```text
stderr
```

para los mensajes generados por Hermes.

Esto permite:

* Mostrar información normal por `stdout`.
* Mostrar errores por `stderr`.
* Mostrar advertencias por `stderr`.
* Redirigir ambos canales independientemente.
* Utilizar colores para distinguir visualmente los mensajes de Hermes.

---

# Canales estándar

| Descriptor | Canal    | Uso                    |
| ---------: | -------- | ---------------------- |
|        `0` | `stdin`  | Entrada estándar       |
|        `1` | `stdout` | Salida estándar        |
|        `2` | `stderr` | Errores y diagnósticos |

RF-11 trabaja principalmente con:

```text
stdout
stderr
```

---

# Módulo `terminal.colors`

Hermes utiliza:

```text
terminal.colors.h
```

como utilidad para centralizar los mensajes generados por la propia aplicación.

La estructura es:

```text
src/include/
└── terminal.colors.h
```

El archivo contiene las funciones:

```cpp
error(...)
warning(...)
info(...)
```

No requiere un archivo `.cpp` independiente porque las funciones utilizan templates.

---

# Función `info()`

La función:

```cpp
info(...)
```

se utiliza para información normal.

Internamente utiliza:

```cpp
std::cout
```

que corresponde a:

```text
stdout
```

Ejemplo:

```cpp
info("job ID: ", job_id);
```

El mensaje se muestra mediante `stdout`.

---

# Función `error()`

La función:

```cpp
error(...)
```

se utiliza para errores de Hermes.

Internamente utiliza:

```cpp
std::cerr
```

que corresponde a:

```text
stderr
```

Ejemplo:

```cpp
error("No se encontró el Job ID: ", job_id);
```

El mensaje se envía a `stderr`.

---

# Función `warning()`

La función:

```cpp
warning(...)
```

también utiliza:

```cpp
std::cerr
```

por lo que su salida corresponde a:

```text
stderr
```

Se utiliza para advertencias o información que no corresponde a la salida normal.

---

# Colores ANSI

Las funciones utilizan códigos ANSI:

| Función     | Canal    | Color    |
| ----------- | -------- | -------- |
| `info()`    | `stdout` | Azul     |
| `warning()` | `stderr` | Amarillo |
| `error()`   | `stderr` | Rojo     |

El color se restablece mediante:

```text
\033[0m
```

Esto evita que el color permanezca activo después del mensaje.

---

# Templates variádicos

Las funciones aceptan múltiples argumentos:

```cpp
template <typename... Args>
void error(const Args&... args)
```

Por ejemplo:

```cpp
error("No se encontró el Job ID: ", job_id);
```

o:

```cpp
info("Job ", job_id, " creado correctamente");
```

No es necesario convertir manualmente los valores:

```cpp
std::to_string(job_id)
```

La implementación utiliza un *fold expression*:

```cpp
(std::cerr << ... << args);
```

o:

```cpp
(std::cout << ... << args);
```

---

# Diferencia entre stderr y un error de ejecución

Es importante distinguir entre:

```text
stderr
```

y:

```text
FAILED
```

Son conceptos diferentes.

`stderr` es un **canal de salida**.

`FAILED` es un **estado del Job**.

Por ejemplo, un programa puede escribir:

```text
sleep: missing operand
```

en `stderr`.

Eso significa que el programa produjo un mensaje mediante el canal de error, pero Hermes determina el estado final del Job mediante el resultado de ejecución del proceso.

Por lo tanto:

```text
stderr ≠ FAILED automáticamente
```

El estado del Job depende del resultado real del proceso.

---

# Salida de procesos hijos

Los programas ejecutados por Hermes también poseen:

```text
stdout
stderr
```

Por ejemplo:

```bash
hermes job echo hola
```

puede producir:

```text
hola
```

mediante el `stdout` del proceso hijo.

En cambio:

```bash
hermes job sleep
```

puede producir:

```text
sleep: missing operand
```

mediante el `stderr` del programa `sleep`.

Este mensaje **no debe pasar por `error()` de Hermes**, ya que pertenece directamente al proceso hijo.

Por esta razón, Hermes no debe colorear automáticamente de rojo toda salida recibida mediante `stderr` de los programas ejecutados.

---

# Herencia de los descriptores

Actualmente, los procesos hijos creados por Hermes heredan los descriptores estándar del proceso padre.

Conceptualmente:

```text
Hermes
 │
 ├── stdout ──────────┐
 │                    │
 └── stderr ──────────┤
                      │
                      ▼
                  proceso hijo
                      │
               ┌──────┴──────┐
               ▼             ▼
            stdout         stderr
```

Por lo tanto, los programas ejecutados pueden escribir directamente en la terminal.

---

# Ejemplo con `stdout`

Al ejecutar:

```bash
hermes job echo hola
```

el proceso hijo ejecuta:

```text
echo hola
```

y produce:

```text
hola
```

mediante `stdout`.

---

# Ejemplo con `stderr`

Al ejecutar:

```bash
hermes job sleep
```

el programa puede producir:

```text
sleep: missing operand
Try 'sleep --help' for more information.
```

Esta salida proviene de `stderr` del programa `sleep`.

Hermes no la genera mediante:

```cpp
error(...)
```

por lo que no se le aplica el color rojo definido para los errores internos de Hermes.

---

# Redirección desde Linux

La separación de canales permite utilizar las herramientas estándar de Linux.

Por ejemplo:

```bash
hermes filter id 10 > salida.txt
```

redirige:

```text
stdout → salida.txt
```

mientras `stderr` permanece en la terminal.

Para redirigir `stderr`:

```bash
hermes filter id 10 2> errores.txt
```

Para combinar ambos:

```bash
hermes filter id 10 > salida.txt 2>&1
```

Esto permite utilizar Hermes desde scripts y otras herramientas de automatización.

---

# Uso desde `main.cpp`

`main.cpp` utiliza las funciones del módulo para mostrar información relacionada con los comandos.

Por ejemplo:

```cpp
error("Comando no reconocido: ", comando);
```

para errores.

Y:

```cpp
info("Uso: hermes job <programa> [argumentos..]");
```

para información normal.

---

# Uso desde `filter.cpp`

El módulo `filter` utiliza las mismas funciones para mantener una salida consistente.

Por ejemplo:

```cpp
error("No se puede abrir: ", archivoJobs);
```

o:

```cpp
error("No se encontró el Job ID: ", job_id);
```

De esta manera, los mensajes generados por Hermes mantienen la separación entre `stdout` y `stderr`.

---

# Relación con los procesos

La arquitectura actual separa dos responsabilidades:

```text
Mensajes de Hermes
        │
        ▼
terminal.colors.h
        │
   ┌────┴────┐
   ▼         ▼
stdout     stderr
```

Mientras que los programas ejecutados utilizan sus propios canales:

```text
Proceso hijo
    │
    ├── stdout
    │
    └── stderr
```

Esto evita mezclar los errores internos de Hermes con los mensajes generados por los programas administrados.

---

# Alcance actual

RF-11 actualmente contempla:

* Uso de `stdout` para información normal de Hermes.
* Uso de `stderr` para errores de Hermes.
* Uso de `stderr` para advertencias.
* Colores ANSI para diferenciar visualmente los mensajes.
* Funciones reutilizables `info()`, `warning()` y `error()`.
* Templates variádicos.
* Separación de los canales estándar.
* Compatibilidad con redirecciones estándar de Linux.
* Conservación de `stdout` y `stderr` de los procesos hijos.
