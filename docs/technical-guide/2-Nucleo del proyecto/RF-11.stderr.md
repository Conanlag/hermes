# RF-11 — Captura separada de stdout y stderr

## Descripción

El requisito funcional RF-11 establece el manejo separado de los canales estándar de salida de los procesos ejecutados por Hermes:

* `stdout`: utilizado para la salida normal del programa.
* `stderr`: utilizado para errores, advertencias y mensajes de diagnóstico.

Para facilitar la identificación de cada tipo de mensaje, Hermes implementa el módulo `terminal.colors`, que permite enviar mensajes a `stdout` o `stderr` utilizando diferentes colores en la terminal.

El módulo utiliza funciones variádicas mediante templates de C++, permitiendo enviar múltiples argumentos de diferentes tipos sin necesidad de realizar conversiones manuales.

---

## Objetivo

Proporcionar un mecanismo centralizado para diferenciar la salida normal de los mensajes de error y advertencia.

La implementación permite:

* Mostrar información normal mediante `stdout`.
* Mostrar errores mediante `stderr`.
* Mostrar advertencias mediante `stderr`.
* Diferenciar visualmente los mensajes utilizando colores ANSI.
* Utilizar las funciones desde cualquier módulo de Hermes.
* Evitar repetir código de colores y redirección en diferentes archivos `.cpp`.

---

## 3. Conceptos de stdout y stderr

Linux proporciona tres canales estándar para la comunicación de los procesos:

| Descriptor | Nombre   | Uso               |
| ---------- | -------- | ----------------- |
| `0`        | `stdin`  | Entrada estándar  |
| `1`        | `stdout` | Salida estándar   |
| `2`        | `stderr` | Salida de errores |

En Hermes, RF-11 se enfoca principalmente en `stdout` y `stderr`.

### stdout

`stdout` se utiliza para mostrar información correspondiente al funcionamiento normal del programa.

Por ejemplo:

```text
Uso: hermes Job <programa> [argumentos..]
```

Este tipo de información se envía mediante la función:

```cpp
info(...)
```

La función utiliza internamente `std::cout`, que corresponde a `stdout`.

---

### stderr

`stderr` se utiliza para mensajes de error y advertencia.

Por ejemplo:

```text
Comando no reconocido: hola
```

Estos mensajes se envían mediante:

```cpp
error(...)
```

o:

```cpp
warning(...)
```

Ambas funciones utilizan `std::cerr`, que corresponde a `stderr`.

Es importante señalar que escribir un mensaje en `stderr` no significa necesariamente que el proceso haya terminado con error. `stderr` es simplemente un canal independiente utilizado normalmente para errores, advertencias y diagnósticos.

El archivo `terminal.colors.h` contiene tanto las declaraciones como la implementación de las funciones, debido a que se utilizan templates de C++.

No es necesario un archivo `terminal.colors.cpp`.

---

## Archivo `terminal.colors.h`

El módulo contiene las funciones:

```cpp
#ifndef TERMINAL_COLORS_H
#define TERMINAL_COLORS_H

#include <iostream>

template <typename... Args>
void error(const Args&... args) {
    std::cerr << "\033[31m";
    (std::cerr << ... << args);
    std::cerr << "\033[0m" << std::endl;
}

template <typename... Args>
void warning(const Args&... args) {
    std::cerr << "\033[33m";
    (std::cerr << ... << args);
    std::cerr << "\033[0m" << std::endl;
}

template <typename... Args>
void info(const Args&... args) {
    std::cout << "\033[34m";
    (std::cout << ... << args);
    std::cout << "\033[0m" << std::endl;
}

#endif
```

---

## Función `error`

La función:

```cpp
template <typename... Args>
void error(const Args&... args);
```

envía los argumentos recibidos a `stderr` mediante `std::cerr`.

Antes de escribir el mensaje se activa el color rojo:

```cpp
std::cerr << "\033[31m";
```

Después del mensaje se restablece el color de la terminal:

```cpp
std::cerr << "\033[0m";
```

Esto permite mostrar los errores visualmente en color rojo.

Ejemplo:

```cpp
error("No se puede abrir: ", archivoJobs);
```

Salida:

```text
No se puede abrir: data/jobs.json
```

La salida se encuentra en `stderr`.

---

## Función `warning`

La función:

```cpp
template <typename... Args>
void warning(const Args&... args);
```

envía mensajes a `stderr`, pero utiliza el código ANSI correspondiente al color amarillo:

```cpp
std::cerr << "\033[33m";
```

Ejemplo:

```cpp
warning("Filtros disponibles: id, status, programa");
```

Esta función se utiliza para mensajes que informan sobre una situación que no necesariamente representa un error de ejecución.

---

## Función `info`

La función:

```cpp
template <typename... Args>
void info(const Args&... args);
```

envía información normal mediante `stdout` utilizando `std::cout`.

El mensaje se muestra en color azul:

```cpp
std::cout << "\033[34m";
```

Ejemplo:

```cpp
info("Uso: hermes Job <programa> [argumentos..]");
```

La salida corresponde a `stdout`.

---

## Uso de templates variádicos

Las funciones utilizan:

```cpp
template <typename... Args>
```

Esto permite que reciban una cantidad variable de argumentos.

Por ejemplo:

```cpp
error("No se encontró el Job ID: ", job_id);
```

donde `job_id` puede ser un `unsigned int`.

También pueden combinar diferentes tipos:

```cpp
info("Job ", job_id, " creado correctamente");
```

No es necesario convertir manualmente los valores a `std::string`.

La expresión:

```cpp
(std::cerr << ... << args);
```

realiza un fold expression que envía todos los argumentos recibidos a `std::cerr`.

De manera equivalente, `info()` utiliza:

```cpp
(std::cout << ... << args);
```

para enviar los argumentos a `stdout`.

---

## Colores utilizados

El módulo utiliza códigos ANSI para modificar temporalmente el color de la terminal:

| Función     | Canal    | Color    | Código ANSI |
| ----------- | -------- | -------- | ----------- |
| `error()`   | `stderr` | Rojo     | `\033[31m`  |
| `warning()` | `stderr` | Amarillo | `\033[33m`  |
| `info()`    | `stdout` | Azul     | `\033[34m`  |
| Restaurar   | —        | Normal   | `\033[0m`   |

El código `\033[0m` es importante porque restaura la configuración de color de la terminal después de mostrar el mensaje.

## Uso desde `main.cpp`

El módulo puede incluirse directamente desde otros archivos:

```cpp
#include "terminal.colors.h"
```

Esto permite utilizar las funciones sin implementar nuevamente la lógica de colores.

### Manejo de comandos no reconocidos

Cuando Hermes recibe un comando que no está definido, se utiliza:

```cpp
error("Comando no reconocido: ", comando);
```

El mensaje se envía mediante `stderr` y se muestra en rojo.

### Mensaje de uso

Cuando Hermes necesita mostrar la sintaxis esperada de un comando, utiliza:

```cpp
info("Uso: hermes Job <programa> [argumentos..]");
```

El mensaje se envía mediante `stdout` y se muestra en azul.

### Advertencias

Para mostrar información adicional sobre las opciones disponibles se utiliza:

```cpp
warning("Filtros disponibles: id, status, programa");
```

El mensaje se envía mediante `stderr` y se muestra en amarillo.

De esta manera, `main.cpp` puede diferenciar entre información normal, advertencias y errores sin implementar directamente los códigos ANSI.

## Uso desde `filter.cpp`

El módulo `filter` también utiliza las funciones de `terminal.colors.h`.

Primero se incluye:

```cpp
#include "terminal.colors.h"
```

### Error al abrir `jobs.json`

Cuando Hermes no puede abrir el archivo de Jobs:

```cpp
error("No se puede abrir: ", archivoJobs);
```

El mensaje se envía a `stderr`.

Por ejemplo:

```text
No se puede abrir: data/jobs.json
```

### Job inexistente

Cuando el filtro por ID no encuentra un Job:

```cpp
error("No se encontró el Job ID: ", job_id);
```

Esto permite combinar texto con el valor numérico de `job_id` sin utilizar concatenaciones mediante `+`.

## Uso correcto de múltiples argumentos

Debido a que las funciones son variádicas, los valores deben separarse mediante comas:

```cpp
error("Job ID: ", job_id);
```

```cpp
info("Programa: ", programa);
```

```cpp
warning("Filtro no reconocido: ", tipoFiltro);
```

No es necesario utilizar:

```cpp
std::to_string(job_id)
```

para convertir valores numéricos.

Tampoco debe utilizarse:

```cpp
error("No se encontró el Job ID: " + job_id);
```

cuando `job_id` es un tipo numérico.

La forma correcta es:

```cpp
error("No se encontró el Job ID: ", job_id);
```

Esto evita realizar operaciones incorrectas entre un literal de texto y un valor numérico.

## Separación entre información y errores

RF-11 establece una separación lógica entre los diferentes tipos de salida.

### Información normal

Utiliza:

```cpp
info(...)
```

Canal:

```text
stdout
```

Ejemplo:

```cpp
info("Uso: hermes Job <programa> [argumentos..]");
```

### Advertencias

Utiliza:

```cpp
warning(...)
```

Canal:

```text
stderr
```

Ejemplo:

```cpp
warning("Filtros disponibles: id, status, programa");
```

### Errores

Utiliza:

```cpp
error(...)
```

Canal:

```text
stderr
```

Ejemplo:

```cpp
error("No se encontró el Job ID: ", job_id);
```

## Redirección de stdout y stderr

La separación de los canales permite redirigir cada salida de manera independiente desde Linux.

Por ejemplo:

```bash
hermes filter id 10 > salida.txt
```

redirige `stdout` al archivo `salida.txt`, mientras que `stderr` continúa mostrándose en la terminal.

También es posible redirigir `stderr`:

```bash
hermes filter id 10 2> errores.txt
```

En este caso, los mensajes generados mediante `error()` y `warning()` se almacenan en `errores.txt`.

Para combinar ambos canales:

```bash
hermes filter id 10 > salida.txt 2>&1
```

Esto permite que Hermes sea utilizado desde scripts y herramientas de automatización aprovechando la separación estándar de los canales de Linux.

## Consideraciones para la ejecución de procesos

La implementación actual de `terminal.colors.h` maneja la salida de la propia aplicación Hermes.

Para la ejecución de procesos hijos, Hermes podrá utilizar posteriormente los descriptores estándar del proceso para capturar de forma independiente:

```text
stdout → salida normal del programa hijo
stderr → errores y diagnósticos del programa hijo
```

Esto permitirá que Hermes almacene, muestre o redirija cada flujo de manera independiente durante la ejecución de Jobs.

Por lo tanto, el módulo `terminal.colors` funciona como una utilidad para la salida de Hermes, mientras que la captura de los flujos de los procesos hijos podrá implementarse mediante mecanismos de procesos e IPC en etapas posteriores del proyecto.
