# RF-05 — Máximo configurable de trabajos simultáneos

## Descripción

Hermes no ejecuta trabajos en paralelo con un número fijo decidido en tiempo de compilación. El máximo de trabajos simultáneos se lee de `config.json` en la llave `trabajos_maximos` y se materializa como el número de hilos trabajadores del scheduler: cada worker supervisa exactamente un proceso hijo a la vez, de modo que el tamaño del pool **es** el límite efectivo de concurrencia.

La configuración se puede cambiar con `hermes configmax <N>`, que valida el rango, serializa la escritura con `config.lock` y deja el archivo consistente mediante escritura atómica. Como el scheduler se ejecuta como demonio, el cambio no altera un pool ya creado: se aplica al siguiente arranque, después de `hermes clean scheduler`.

El diseño evita dos fuentes de verdad. El límite que decide cuántos procesos se lanzan y el que decide cuántos Jobs se admiten son el mismo número para la concurrencia; la capacidad de espera se declara aparte con `max_cola` (RF-03), de forma que subir o bajar el paralelismo no cambia implícitamente el tamaño de la cola.

---

## Objetivo

Permitir que el operador fije cuántos trabajos se ejecutan a la vez y garantizar que el scheduler nunca supere ese valor, independientemente de cuántas solicitudes lleguen.

> "El sistema deberá permitir configurar un máximo de trabajos simultáneos y respetarlo."

**Consideraciones actuales:**

- **Sí hace:** leer `trabajos_maximos` en cada invocación, validar el rango `[1, 64]` y crear exactamente esa cantidad de workers al iniciar el scheduler.
- **Sí hace:** aplicar un default seguro de `5` con evento `WARN` cuando el archivo falta, está corrupto o el valor es inválido.
- **Sí hace:** ofrecer `hermes configmax <N>` como vía validada y atómica para cambiar el valor, y `hermes configmax --cola <M>` para los cupos de espera. Con ambos argumentos se validan y persisten juntos en una única transacción.
- **No hace:** aplicar el cambio en caliente sobre un scheduler activo; requiere `hermes clean scheduler` y un comando posterior que lo reinicie.
- **No hace:** aceptar límites por usuario, por cola o por tipo de Job; el límite es global para la instancia.
- **No hace:** corregir a mano un `config.json` inválido: si el archivo no parsea, la carga cae a los valores por defecto con `WARN`, así que la vía recomendada es siempre el CLI.
- **No hace:** redimensionar el pool si el archivo cambia mientras el demonio está vivo, aunque otro proceso CLI lea el valor nuevo.

## Estructura del módulo

```text
src/hermes/
├── include/
│   ├── config.h            # Constantes de rango y ConfiguracionSistema
│   ├── data_paths.h        # Crea config.json por defecto con trabajos_maximos: 5
│   └── scheduler.h         # iniciarSchedulerSiNecesario(int), ejecutarScheduler(int)
└── src/
    ├── config/config.cpp        # cargarConfiguracion(): parseo tolerante
    ├── config/config_update.cpp # establecerTrabajosMaximos(): configmax
    ├── scheduler/scheduler.cpp  # pool de N workers
    └── main.cpp                 # carga, arranque del demonio y paso a crearJob()
```

| Archivo / directorio | Responsabilidad |
| --- | --- |
| `include/config.h` | Declara `DEFAULT_TRABAJOS_MAXIMOS = 5`, `MIN_TRABAJOS_MAXIMOS = 1`, `MAX_TRABAJOS_MAXIMOS = 64` y el campo `trabajosMaximos`. |
| `include/data_paths.h` | Genera `config.json` inicial con `{"trabajos_maximos": 5}` cuando no existe. |
| `include/scheduler.h` | Declara el arranque del demonio y la ejecución del pool con el límite como parámetro. |
| `src/config/config.cpp` | Lee y valida la llave; nunca lanza excepción por configuración inválida. |
| `src/config/config_update.cpp` | Valida rango, toma `config.lock`, reescribe la llave y registra el cambio. |
| `src/scheduler/scheduler.cpp` | Crea tantos hilos como indique el parámetro y los ejecuta hasta el apagado. |
| `src/main.cpp` | Punto de unión: carga la configuración, arranca el demonio y propaga el valor a la admisión. |

## Definición de los estados

El límite no introduce estados nuevos; opera sobre los existentes:

| Estado | Relación con el límite |
| --- | --- |
| `RUNNING` | Es el estado acotado. Nunca hay más Jobs `RUNNING` que workers, porque cada worker atiende un Job a la vez. |
| `QUEUED` | Espera un worker libre. Su cantidad no la fija `trabajos_maximos`, sino `max_cola`. |
| Terminales | Al liberar un worker, el siguiente `QUEUED` pasa a `RUNNING`. |

`Status` se persiste como texto (`"RUNNING"`, `"QUEUED"`, …) y se convierte en `status.cpp`; el límite se evalúa sobre esos textos, no sobre el enum, para poder auditar `jobs.json` directamente.

## Implementación de `.h`

**Propósito:** centralizar los rangos válidos y transportar el valor ya validado entre capas.

**Constantes:**

```cpp
constexpr int DEFAULT_TRABAJOS_MAXIMOS = 5;
constexpr int MIN_TRABAJOS_MAXIMOS = 1;
constexpr int MAX_TRABAJOS_MAXIMOS = 64;

struct ConfiguracionSistema {
    int trabajosMaximos = DEFAULT_TRABAJOS_MAXIMOS;
    int maxCola = DEFAULT_MAX_COLA;
};
```

**Contrato del scheduler:** el límite entra como argumento, no como constante global. Esa decisión es la que permite que el pool sea dinámico sin tocar el motor:

```cpp
void iniciarSchedulerSiNecesario(int trabajosMaximos = 5);
void ejecutarScheduler(int trabajosMaximos = 5);
```

**Actualización validada:** el CLI no llama a la persistencia directamente. Describe el cambio en una estructura de intenciones y deja que `actualizarConfiguracion()` valide, bloquee y escriba una sola vez.

```cpp
struct CambiosConfiguracion {
    bool trabajosMaximos = false;
    int valorTrabajosMaximos = 0;
    bool maxCola = false;
    int valorMaxCola = 0;
};

void actualizarConfiguracion(const CambiosConfiguracion& cambios);
void establecerTrabajosMaximos(int trabajosMaximos);  // atajo
void establecerMaxCola(int maxCola);                  // atajo
```

Lanza `std::invalid_argument` fuera de rango y `std::runtime_error` si el archivo no se puede leer o escribir.

## Implementación de `.cpp`

**Carga tolerante (`config.cpp`).** Cada modo de fallo devuelve una configuración usable y deja rastro en la bitácora: archivo que no abre, JSON que no parsea, JSON que no es objeto, llave ausente o no entera, y valores fuera de rango (que se ajustan al límite más cercano, sin reescribir el archivo).

```cpp
if (!datos.contains("trabajos_maximos") ||
    !datos["trabajos_maximos"].is_number_integer()) {
    EventLog::log_event_system(
        EventLevel::WARN,
        "Llave 'trabajos_maximos' ausente o no entera en config.json",
        {{"archivo", ruta}, {"trabajos_maximos", config.trabajosMaximos}}
    );
    return config;
}
```

**Actualización atómica (`config_update.cpp`).** `actualizarConfiguracion()` sigue tres pasos: valida todas las claves activas antes de tocar el disco, toma `config.lock`, y reescribe el objeto JSON preservando las llaves que no se modifican. El guardado delega en `guardarAtomico` (temporal exclusivo, `fsync`, `rename` y `fsync` del directorio). Como la validación precede a la escritura, un `hermes configmax 4 --cola 999` no deja `trabajos_maximos` a medias.

```cpp
void actualizarConfiguracion(const CambiosConfiguracion& cambios) {
    if (cambios.trabajosMaximos) {
        validarRango(cambios.valorTrabajosMaximos,
                     MIN_TRABAJOS_MAXIMOS, MAX_TRABAJOS_MAXIMOS,
                     "trabajos_maximos");
    }
    if (cambios.maxCola) {
        validarRango(cambios.valorMaxCola,
                     MIN_MAX_COLA, MAX_MAX_COLA, "max_cola");
    }

    BloqueoConfiguracion bloqueo;   // config.lock
    ...
    if (cambios.maxCola) {
        datos["max_cola"] = cambios.valorMaxCola;
    }
    guardarAtomico(ruta, datos);
}
```

**Pool (`scheduler.cpp`).** El tamaño del pool es el parámetro y no se recalcula después:

```cpp
void ejecutarScheduler(int trabajosMaximos) {
    instalarHandlersDeApagado();
    std::thread coordinador(coordinarApagado);

    vector<thread> trabajadores;
    trabajadores.reserve(trabajosMaximos);
    for (int i = 0; i < trabajosMaximos; ++i) {
        trabajadores.emplace_back(trabajador);
    }
    // join de todos los workers y del coordinador
}
```

Cada `trabajador()` reserva un Job, lanza un proceso hijo y bloquea en `esperarProceso` hasta que termina; en ningún momento un hilo atiende dos procesos a la vez.

**Arranque único.** `iniciarSchedulerSiNecesario` abre `scheduler.lock` con `flock(LOCK_EX | LOCK_NB)`; si otro demonio lo tiene, retorna sin mirar el valor recibido. Esa es la razón de que el límite se aplique al arrancar y no en cada invocación.

## Integración con `main`, `configmax` y `job`

```cpp
config = hermes::cargarConfiguracion();
iniciarSchedulerSiNecesario(config.trabajosMaximos);
...
job = crearJob(programa, argumentos, requestId,
               config.trabajosMaximos, config.maxCola);
```

- **`main.cpp`** carga la configuración antes de crear el Job, de modo que la admisión y el pool usan el mismo número en una misma invocación.
- **`configmax`** es la interfaz de cambio: parsea `<N>`, `--cola <M>` o ambos en cualquier orden, valida cada valor con su propio rango y persiste en una sola transacción.

```text
$ hermes configmax 10
Máximo de trabajos simultáneos configurado en 10. El cambio de workers se aplica al iniciar el scheduler.

$ hermes configmax --cola 2
Cupos de espera (max_cola) configurados en 2. El cambio se aplica al iniciar el scheduler.

$ hermes configmax 5 --cola 1
Máximo de trabajos simultáneos configurado en 5. El cambio de workers se aplica al iniciar el scheduler.
Cupos de espera (max_cola) configurados en 1. El cambio se aplica al iniciar el scheduler.

Para aplicarlo ahora, ejecute 'hermes clean scheduler'; los trabajos en ejecución serán interrumpidos.
```

Un valor fuera de rango se rechaza sin escribir nada:

```text
$ hermes configmax --cola 257
El valor de --cola debe estar entre 0 y 256.
```

- **`job.cpp`** usa el valor como límite de concurrencia dentro de la capacidad total de admisión (`trabajosMaximos + maxCola`), nunca como sustituto de la cola.

## Integración con RF-03 y RNF-07

RF-05 define el número; RF-03 define qué pasa con el excedente; RNF-07 exige que ese número no se desborde. Los tres se sostienen sobre la misma decisión: **`trabajos_maximos` acota procesos, no registros**. Antes de ADR-017 la llave acotaba ambas cosas, y eso hacía que la cola nunca pudiera llenarse porque el pool ya consumía todos los cupos de admisión.

## Ejemplo de funcionamiento

```bash
$ ./hermes configmax 3 --cola 1
Máximo de trabajos simultáneos configurado en 3. El cambio de workers se aplica al iniciar el scheduler.
Cupos de espera (max_cola) configurados en 1. El cambio se aplica al iniciar el scheduler.
Para aplicarlo ahora, ejecute 'hermes clean scheduler'; los trabajos en ejecución serán interrumpidos.

$ ./hermes clean scheduler
Scheduler detenido correctamente.

$ cat "$HOME/.local/share/hermes/data/config.json"
{
    "max_cola": 1,
    "trabajos_maximos": 3
}

$ ./hermes job sleep 10 &   # x4
job ID: 1
job ID: 2
job ID: 3
job ID: 4
```

Estado resultante:

```json
[
  { "job_id": 1, "status": "RUNNING", "pid": 8451 },
  { "job_id": 2, "status": "RUNNING", "pid": 8452 },
  { "job_id": 3, "status": "RUNNING", "pid": 8453 },
  { "job_id": 4, "status": "QUEUED",  "pid": 0 }
]
```

Tres procesos hijo como máximo; el cuarto espera. Verificación automatizada:

```bash
bash verif/scripts/TC-002.sh
```

```text
Paso 2 OK (trabajos_maximos=3, max_cola=1)
Paso 5 OK (3 Jobs RUNNING con límite 3)
[ PASS ] TC-002
```

> Nota de trazabilidad: la matriz cita `TC-025` para RF-05, pero esa prueba no está presente en `verif/scripts/` de esta rama. La evidencia vigente del límite configurable es `TC-002`, ejecutada en WSL con `trabajos_maximos = 3`.
