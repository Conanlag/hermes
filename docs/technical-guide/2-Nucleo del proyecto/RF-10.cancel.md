# RF-10 — Cancelación de trabajos

## Descripción

El requisito RF-10 permite al usuario solicitar la cancelación de un trabajo en cola o en ejecución, y refleja el resultado en el estado persistido. Es la primera operación de Hermes que combina escritura en disco con señales del sistema: marca la intención en `jobs.json` y, cuando existe un proceso real, inicia la política `SIGTERM` → gracia → `SIGKILL` de RF-30.

El diseño separa dos casos con naturalezas distintas. Un trabajo `QUEUED` aún no tiene proceso (`pid = 0`), así que se cancela de forma directa y síncrona marcando `CANCELED`. Un trabajo `RUNNING` ya tiene proceso y supervisor activos, así que la cancelación es asíncrona: se registra `cancel_requested` bajo el bloqueo de almacenamiento y, si el PID está disponible, se aplica la política de escalamiento; el supervisor confirma y persiste el estado final. Si el PID todavía es `0`, el scheduler envía `SIGTERM` al guardarlo.

El módulo `cancel` orquesta: usa `modificarJobsSeguros` de `storage`, la política de proceso de RF-30, la validación de ID de RF-02 y el estado compartido con el scheduler.

---

## Objetivo

La meta técnica exacta es cancelar en ambos estados con mensajes que expliquen la causa de cada rechazo y sin romper a los consumidores existentes.

> El usuario deberá poder solicitar la cancelación de un trabajo en cola o en ejecución; el sistema deberá reflejar el resultado.

Consideraciones actuales:
- Hace: `QUEUED` → `CANCELED` directo con `codigo_salida = -1`, sin señal, mensaje `Job cancelado:`.
- Hace: `RUNNING` → registra flag y, si `pid > 0`, aplica escalamiento de `SIGTERM` a `SIGKILL` tras cinco segundos; el supervisor persiste `CANCELED` con el código de salida de la señal.
- Hace: rechazos con causa (`NO_EXISTE` → `No existe el Job ID:`, `NO_CANCELABLE` → `El Job no se puede cancelar (estado: X)...`, fallos de archivo/PID/señal con detalle) y `cancelarJob` original preservada como envoltorio.
- NO hace: cancelación de `SUCCEEDED`, `FAILED` o `CANCELED` (se rechazan con el estado actual).
- NO hace: deduplicación de solicitudes concurrentes para el mismo Job; cada llamada puede iniciar su propia secuencia de señales (RF-26).
- NO hace: escalamiento a `SIGKILL` cuando el PID aún es `0`; en ese caso el scheduler envía `SIGTERM` al guardar el PID (RF-30).

## Definición de los estados

Reutiliza `Status` sin crear estados nuevos, más el veredicto propio de la operación:

```cpp
enum class CodigoCancelacion {
    CANCELADO,
    SOLICITUD_REGISTRADA,
    NO_EXISTE,
    NO_CANCELABLE,
    ERROR_LECTURA
};
```

| Código | Cuándo | Efecto en disco/proceso |
| ------ | ------ | ----------------------- |
| `CANCELADO` | Job `QUEUED` | `status = CANCELED`, `codigo_salida = -1`. Sin señal. Inmediato. |
| `SOLICITUD_REGISTRADA` | Job `RUNNING` | `cancel_requested = true`; con PID positivo se ejecuta RF-30, y con PID `0` el scheduler envía `SIGTERM` al guardar el PID. El supervisor persiste `CANCELED`. |
| `NO_EXISTE` | ID ausente | Sin efectos. Mensaje `No existe el Job ID:`. |
| `NO_CANCELABLE` | `SUCCEEDED`, `FAILED` o `CANCELED` | Sin efectos. Mensaje con el estado actual. |
| `ERROR_LECTURA` | Archivo ilegible, JSON roto, estado/PID ilegible, señal fallida | Sin efectos garantizados. Mensaje con detalle. |

## Implementación de `.h`

**1. Propósito.** `cancel.h` promete dos sabores: el booleano histórico y el detallado con causa. Nada más.

**2. Dependencias.** Solo `<string>` para el mensaje del resultado. No incluye `job.h` ni JSON: el contrato no expone persistencia.

**3. Estructuras.**

```cpp
enum class CodigoCancelacion {
    CANCELADO,
    SOLICITUD_REGISTRADA,
    NO_EXISTE,
    NO_CANCELABLE,
    ERROR_LECTURA
};

struct ResultadoCancelacion {
    bool exito;
    CodigoCancelacion codigo;
    string mensaje;
};
```

**4. Prototipos.**

```cpp
bool cancelarJob(unsigned int jobId);
ResultadoCancelacion cancelarJobDetallado(unsigned int jobId);
```

Se mantuvo `cancelarJob` intacta como envoltorio (`return detallado.exito`) para no romper consumidores. La nueva función documenta en su comentario las cinco ramas.

## Implementación de `.cpp`

### Búsqueda y ramificación por estado

`cancelarJobDetallado` busca y modifica el Job dentro de `modificarJobsSeguros`. La comprobación del estado y la transición quedan protegidas por el mismo bloqueo:

```cpp
if (estado == "QUEUED") {
    item["status"] = "CANCELED";
    item["codigo_salida"] = -1;
    item["tiempo_terminacion"] = obtenerFechaHoraActual();
    canceladoEnCola = true;
    return true;
}

if (estado == "RUNNING") {
    item["cancel_requested"] = true;
    pid = item.value("pid", 0);
    solicitudRegistrada = true;
    return true;
}
```

Después de la modificación, `cancelarJobDetallado` traduce esas marcas locales a `CANCELADO` o `SOLICITUD_REGISTRADA`. Los demás estados se rechazan citando el estado encontrado. Los errores que lanza el almacenamiento se convierten en `ERROR_LECTURA` con el mensaje de la excepción.

### Camino `RUNNING`: marca y política de proceso

```cpp
item["cancel_requested"] = true;
pid = item.value("pid", 0);

if (pid > 0) {
    if (!escalarCancelacionProceso(pid, 5)) {
        return {false, CodigoCancelacion::ERROR_LECTURA,
                "No se pudo completar la solicitud de cancelación."};
    }
}
```

La marca y lectura del PID ocurren dentro de la modificación segura del JSON; la secuencia de señales comienza después de publicar esa modificación. Si el PID aún es `0`, `guardarPid` del scheduler detecta la marca y envía `SIGTERM`. Si el PID es positivo, `escalarCancelacionProceso` aplica la política documentada en RF-30.

### Cierre

Si el recorrido termina sin match: `{false, NO_EXISTE, "No existe el Job."}`. `main.cpp` lo traduce a `No existe el Job ID: <n>`.

## Integración con `main.cpp`, `job`, `process` y `validator`

`main.cpp` valida existencia (`argc < 3`) y contenido (`validarIdTexto`, RF-02) antes de convertir con `stoul` ya seguro, luego delega y traduce cada código:

```cpp
ResultadoCancelacion cr = cancelarJobDetallado(id);

if (!cr.exito) {
    if (cr.codigo == CodigoCancelacion::NO_EXISTE) {
        error("No existe el Job ID: ", id);
    } else if (cr.codigo == CodigoCancelacion::NO_CANCELABLE) {
        error(cr.mensaje);
    } else {
        error("No se pudo cancelar el Job: ", id, ". ", cr.mensaje);
    }
    return 1;
}

if (cr.codigo == CodigoCancelacion::CANCELADO) {
    info("Job cancelado: ", id);
} else {
    info("Cancelación solicitada para el Job: ", id);
}
```

Nota: `./hermes cancel <1>` sin comillas nunca llega al programa: `bash` interpreta `<` y `>` como redirección y falla con `syntax error`. Con comillas (`"<1>"`) sí llega y RF-02 lo rechaza como mal formado.

## Integración con RF-01, RF-02, RF-06 y RF-08

Culmina la cadena: RF-01 crea y supervisa, RF-02 valida el ID de entrada, RF-06 provee el vocabulario de estados y RF-26 serializa las modificaciones concurrentes. RF-30 define las señales del proceso. El trabajador de RF-01 confirma la rama `RUNNING` al recolectar el proceso y persiste el estado final.

## Ejemplo de funcionamiento

**1. Cancelación en ejecución:**

```bash
./hermes job sleep 30
./hermes cancel 5
./hermes filter id 5
```

```text
job ID: 5
Cancelación solicitada para el Job: 5
Job ID: 5
PID: 1556
Programa: sleep
Estado: CANCELED
Codigo de salida: -15
Argumentos: 30
```

El `-15` es `-SIGTERM`: prueba de que el proceso murió por la señal y el supervisor persistió el estado.

**2. Cancelación en cola (ID 999 plantado como `QUEUED`, `pid 0`):**

```bash
./hermes cancel 999
./hermes filter id 999
```

```text
Job cancelado: 999
Job ID: 999
PID: 0
Programa: sleep
Estado: CANCELED
Codigo de salida: -1
Argumentos: 30
```

**3. Rechazos con causa:**

```bash
./hermes cancel 999999
./hermes cancel 1
```

```text
No existe el Job ID: 999999
El Job no se puede cancelar (estado: SUCCEEDED). Solo QUEUED o RUNNING.
```

`data/jobs.json` solo cambia en los dos casos exitosos: `CANCELED` con `cancel_requested` marcado.
