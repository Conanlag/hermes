# TC-018: Tratamiento idempotente de solicitudes duplicadas

**Requisitos cubiertos:** RF-27
**Métodos de verificación:** Según la matriz de trazabilidad.
**Nivel de prueba:** Integración

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Comprobar que solicitudes de creación concurrentes con el mismo `request-id` y los mismos argumentos reutilicen un único Job; que el mismo identificador con argumentos incompatibles se rechace sin alterar el Job existente; y que un reintento posterior a la terminación preserve el identificador, estado y tiempo de terminación originales.
* **Precondiciones:** Disponer de un clon limpio del repositorio en Linux, Hermes compilado y ejecutable, Bash y Perl con el módulo `JSON::PP`. El caso utiliza un `HOME` temporal aislado y no debe depender de datos de Jobs preexistentes.
* **Entorno y configuración:** Distribución Linux en entorno controlado; compilación con GCC o Clang. No se requiere LAN ni VPN. La prueba usa un `HOME` temporal con la configuración predeterminada de Hermes; el límite de concurrencia está definido por `config.json` (por defecto, 5 workers y capacidad de admisión de 5 Jobs). No se modifica la configuración del usuario. Se requiere acceso a `/proc` para localizar y detener el scheduler aislado.
* **Datos de entrada:** Ocho invocaciones concurrentes de `hermes job --request-id rf27-concurrent sleep 30`; un reintento con ese mismo identificador y el argumento `sleep 31`; una solicitud sin `request-id` (`sleep 30`); y una solicitud con identificador `rf27-terminal` y programa `true`, seguida de un reintento idéntico después de que termine.
* **Pasos reproducibles:**
  1. Desde la raíz del repositorio, compilar Hermes ejecutando `make -C src/hermes`.
  2. Ejecutar `bash verif/scripts/TC-018.sh`.
  3. Esperar a que el script termine y revisar su código de salida, la salida de consola y el registro `verif/results/results_TC-018.md`.
* **Resultado esperado:** El script termina con código `0` y muestra `PASS: claves repetidas son atomicas, reutilizan el Job y rechazan payloads distintos.` Las ocho solicitudes concurrentes con el mismo identificador deben devolver un único ID y `jobs.json` debe contener un solo Job asociado a `rf27-concurrent`. El reintento con argumentos incompatibles debe fallar, producir un mensaje que indique que el identificador ya corresponde a otro programa o argumentos y no agregar ni modificar registros. La solicitud sin identificador debe crear un Job independiente. Tras finalizar el Job `rf27-terminal`, repetir la solicitud debe devolver el mismo ID y conservar su estado `SUCCEEDED` y su tiempo de terminación.
