### [TC-007]: Reinicio y recuperación
**Requisitos cubiertos:** RF-12, RF-13, RNF-10, RNF-11  
**Métodos de verificación:** Prueba  
**Nivel de prueba:** Robustez

#### 1. Fase de Diseño (Planificación)

- **Objetivo:** Verificar la capacidad de resiliencia y reconciliación de estado del daemon Hermes tras una interrupción abrupta (simulando una caída o corte de energía). Se debe comprobar que los trabajos en estado `RUNNING` que pierden supervisión transicionen coherentemente a `INTERRUPTED` al reiniciar el sistema, sin borrar el historial previo (RF-12, RF-13), que no se reporte ningún trabajo `RUNNING` falsamente (RNF-10) y que las escrituras a `jobs.json` soporten el reinicio sin corromper el formato JSON mediante escrituras atómicas (RNF-11).

- **Precondiciones:** 
  1. Repositorio clonado limpio.
  2. Proyecto compilado con `make` en un entorno Linux/WSL.
  3. Directorio de datos `$HOME/.local/share/hermes/data/` accesible.
  4. Sin instancias activas del scheduler al iniciar la prueba.
  5. Límite de concurrencia definido en `config.json`.

- **Entorno y configuración:** 
  - SO: Linux (WSL)
  - Compilador: GCC/Clang
  - Entorno aislado con `HOME` temporal para no alterar datos reales.
  - Sondas de proceso (`kill -0`) y lectura de PIDs para inyección de fallos.
  - Comprobación de persistencia atómica mediante `fsync` y temporales.

- **Datos de entrada:**
  1. Envío de un trabajo de larga duración: `hermes job sleep 60`
  2. Inyección de señal fatal al proceso daemon supervisor: `kill -9 <PID_SCHEDULER>`
  3. Ejecución de un comando de consulta para forzar la rutina de recuperación en arranque: `hermes filter status RUNNING`

- **Pasos reproducibles:** 
  1. **Preparación:** Inicializar un entorno aislado estableciendo un `HOME` temporal (`mktemp -d`).
  2. **Ejecución:** Lanzar un trabajo de larga duración en background (`hermes job sleep 60 &`).
  3. **Extracción de PID:** Localizar el PID del proceso daemon de Hermes que mantiene el bloqueo sobre `scheduler.lock`.
  4. **Interrupción (Caída Abrupta):** Enviar `SIGKILL` al proceso daemon extraído en el paso anterior para simular una muerte repentina sin oportunidad de ejecutar apagado ordenado.
  5. **Recuperación:** Ejecutar un comando pasivo del CLI (`hermes filter status RUNNING`) para obligar al sistema a leer el archivo de persistencia y disparar el módulo de recuperación (Fase pre-fork).
  6. **Verificación de Resiliencia (RNF-10, RF-13):** Comprobar la salida del comando anterior para certificar que el trabajo fue reclasificado y **no** figura como `RUNNING`.
  7. **Verificación de Historial y Diagnóstico (RF-12):** Consultar el estado del trabajo con `hermes filter id <jobId>` para verificar la transición a `INTERRUPTED`, la presencia del código `-1`, y la explicación forense del `motivo`.
  8. **Verificación de Integridad Atómica (RNF-11):** Inspeccionar físicamente el archivo `jobs.json` con un validador JSON estricto (`python3 -c "import json..."`) para comprobar que ninguna estructura quedó truncada por la caída.

- **Resultado esperado:** 
  1. El sistema no bloquea ni falla al arrancar tras la muerte del daemon anterior.
  2. El trabajo originalmente `RUNNING` transiciona irrevocablemente al estado terminal `INTERRUPTED`. No quedan trabajos marcados como `RUNNING` en la base de datos ni en el listado CLI.
  3. El diagnóstico del trabajo refleja un código de salida `-1` y el campo `motivo` indica "caída" (o el mensaje textual equivalente de reinicio).
  4. Los metadatos originales del trabajo (`programa`, `recepcion`) permanecen intactos.
  5. El archivo `jobs.json` y la bitácora `events.jsonl` son archivos de texto JSON perfectamente válidos y parseables.

#### 2. Fase de Ejecución (Resultados empíricos)
- **Resultado observado:** Se encoló un trabajo de larga duración y se inyectó la señal SIGKILL directamente al proceso daemon (PID extraído de scheduler.lock). Al invocar un filtro RUNNING, el motor se percató de la caída, aplicó la rutina de recuperación pre-fork, y limpió exitosamente al proceso huérfano. El trabajo transicionó correctamente a INTERRUPTED con código -1 y su diagnóstico de caída, evitando falsos reportes de trabajos RUNNING. El archivo jobs.json demostró una escritura atómica y estrictamente parseable.
