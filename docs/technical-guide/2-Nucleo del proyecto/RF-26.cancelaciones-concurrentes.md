# RF-26 — Cancelaciones concurrentes coherentes

## Descripción

RF-26 garantiza que las cancelaciones y las transiciones de estado realizadas por los trabajadores operen sobre una persistencia común sin sobrescribirse parcialmente. La cancelación y el scheduler modifican `jobs.json` mediante `modificarJobsSeguros`: el mutex local coordina hilos del mismo proceso y `flock` coordina procesos que comparten el archivo de bloqueo. Los cambios aceptados se escriben en un temporal y se publican mediante `rename`.

La comprobación del estado y su cambio pertenecen a una misma operación protegida. Por eso, si el scheduler reserva primero un Job, la cancelación encuentra `RUNNING` y marca `cancel_requested`; si la cancelación de un Job `QUEUED` gana primero, lo cambia a `CANCELED` y el scheduler ya no lo reserva. Si el PID todavía no se ha guardado, el trabajador detecta la marca al registrar el PID y envía `SIGTERM`.

Dos comandos `cancel` concurrentes sobre el mismo Job pueden observar `RUNNING` y registrar `cancel_requested = true`. La escritura sigue siendo coherente y ambas solicitudes pueden responder como registradas, pero el sistema no deduplica las solicitudes ni garantiza una única escalada de señales. RF-26 protege la integridad y consistencia de la persistencia compartida; no implementa exclusión por Job durante la fase de señales.

---

## Objetivo

Evitar transiciones perdidas o archivos JSON corruptos cuando varias operaciones de Hermes actualizan simultáneamente un Job.

Consideraciones actuales:
- Hace: serializa lectura-modificación-escritura de `jobs.json` con mutex y `flock`.
- Hace: reemplaza el JSON completo mediante un archivo temporal y `rename`.
- Hace: coordina atómicamente la reserva `QUEUED` → `RUNNING` del scheduler y la cancelación `QUEUED` → `CANCELED`.
- Hace: conserva `cancel_requested` cuando la cancelación alcanza un Job `RUNNING`; el supervisor lo consulta al guardar el PID y al finalizar el trabajo.
- NO hace: deduplicación de dos solicitudes concurrentes de cancelación para el mismo Job.
- NO hace: bloqueo exclusivo por Job durante el envío y la escalada de señales.
- NO hace: garantizar que cualquier error del sistema de archivos o de proceso pueda recuperarse sin intervención; los errores de persistencia se propagan al llamador.


| Archivo / directorio | Responsabilidad |
| -------------------- | --------------- |
| `include/storage.h` | Expone lectura y modificación segura del arreglo de Jobs |
| `src/storage/storage.cpp` | Coordina hilos y procesos, bloquea el archivo y guarda con reemplazo atómico |
| `src/cancel/cancel.cpp` | Marca el Job como cancelado o registra una solicitud para un Job en ejecución |
| `src/scheduler/scheduler.cpp` | Reserva trabajos, registra PID y persiste el resultado final |
| `src/process/process.cpp` | Ejecuta la política de señales para el PID disponible |
| `$HOME/.local/share/hermes/data/jobs.json` | Estado persistido compartido por el CLI y el scheduler; accesible desde `src/hermes/data/jobs.json` |
| `$HOME/.local/share/hermes/data/jobs.lock` | Archivo usado por `flock` como punto de coordinación entre procesos; accesible desde `src/hermes/data/jobs.lock` |

El mismo directorio contiene `config.json` (configuración inicial) y `scheduler.lock` (bloqueo del scheduler). La función de cada archivo está descrita en [Estructura del proyecto](./Estructura%20del%20proyecto.md#directorio-de-datos-persistentes).

## Definición de los estados

RF-26 no agrega valores al `enum Status`. Las transiciones relevantes son:

| Estado / marca | Significado | Efecto de una cancelación |
| -------------- | ----------- | ------------------------- |
| `QUEUED` | Job aún no reservado por un trabajador | Cambia directamente a `CANCELED`; el scheduler ya no lo selecciona |
| `RUNNING`, PID `0` | Reservado, proceso aún sin PID persistido | Registra `cancel_requested`; al guardar el PID, el trabajador envía `SIGTERM` |
| `RUNNING`, PID positivo | Proceso asociado disponible | Registra `cancel_requested` y ejecuta la política de cancelación |
| `CANCELED` | Estado final de un Job cancelado | El scheduler lo persiste al finalizar al observar la marca |

`cancel_requested` es una marca booleana, no un estado. El resultado final se escribe después de que el trabajador recolecta el proceso.

## Implementación de `.h`

`storage.h` ofrece el punto común de acceso al JSON:

```cpp
json leerJobsSeguros();
bool modificarJobsSeguros(
    const std::function<bool(json&)>& funcion
);
```

La función recibe una operación sobre el arreglo completo. Devuelve `true` cuando la función modificadora acepta el cambio y este se persiste; una excepción indica un fallo de lectura o escritura. Los encabezados `cancel.h` y `scheduler.h` mantienen sus contratos de dominio y no exponen mutexes ni descriptores de bloqueo.

---

## Implementación de `.cpp`

`modificarJobsSeguros` aplica esta secuencia:

1. Adquiere el `std::mutex` del proceso.
2. Abre `jobs.lock` y adquiere `flock(LOCK_EX)`.
3. Lee y valida el arreglo de `jobs.json`.
4. Ejecuta la función que actualiza el arreglo.
5. Si la función acepta el cambio, escribe un archivo temporal y lo publica con `rename`.
6. Libera el bloqueo al salir del ámbito, incluso ante una excepción.

El flujo de cancelación verifica el estado dentro de esa misma sección crítica:

```cpp
if (estado == "QUEUED") {
    item["status"] = "CANCELED";
    item["codigo_salida"] = -1;
    item["tiempo_terminacion"] = obtenerFechaHoraActual();
    return true;
}

if (estado == "RUNNING") {
    item["cancel_requested"] = true;
    pid = item.value("pid", 0);
    return true;
}
```

El scheduler usa el mismo mecanismo al reservar (`QUEUED` → `RUNNING`), al guardar el PID y al registrar el resultado. Cada escritura lee el estado más reciente dentro del bloqueo y publica el arreglo completo; no mantiene una copia privada que reemplace cambios de otros escritores.

## Integración con `cancel`, `scheduler`, `process` y `storage`

`cancelarJobDetallado` cambia o marca el registro bajo `modificarJobsSeguros`. Después de liberar el bloqueo, si guardó la solicitud y obtuvo un PID positivo, invoca `escalarCancelacionProceso`. Si el PID era `0`, no intenta señalizarlo: `guardarPid` del scheduler ve `cancel_requested` y envía `SIGTERM` cuando el PID ya existe.

Al terminar, el scheduler vuelve a leer el Job bajo el mismo mecanismo seguro. Si la marca continúa activa, guarda `CANCELED`; de otro modo decide entre `SUCCEEDED` y `FAILED` según el resultado del proceso.

## Integración con RF-10, RF-30 y RF-06

- RF-10 define el comando de cancelación y sus resultados.
- RF-30 define la política de señales para un PID ya disponible.
- RF-06 define los estados finales existentes; RF-26 no añade otro estado.
- RF-01 aporta el scheduler que reserva, ejecuta y finaliza trabajos.

## Ejemplo de funcionamiento

La prueba de integración correspondiente es [TC-019](../../../verif/test-cases/TC-019.md). Su script `verif/scripts/TC-019.sh` registra cada ejecución en `verif/results/results_TC-019.md`.

Dos cancelaciones pueden ejecutarse simultáneamente contra un Job `RUNNING`:

```bash
hermes cancel 42 &
hermes cancel 42 &
wait
hermes filter id 42
```

Ambas modificaciones del JSON se serializan. Un resultado compatible con el comportamiento actual es:

```text
Cancelación solicitada para el Job: 42
Cancelación solicitada para el Job: 42
...
Estado: CANCELED
```

Las dos respuestas indican que la marca pudo registrarse, no que cada comando represente una cancelación independiente ni que solo se hayan enviado señales una vez. El criterio de coherencia es que `jobs.json` siga siendo JSON válido y el Job termine reflejando una cancelación solicitada.
