# TC-040: El cliente reporta los sobres de error de protocolo

**Requisitos cubiertos:** RNF-14
**Métodos de verificación:** Prueba
**Nivel de prueba:** Funcional e integración

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Verificar que el cliente interpreta los sobres de error que emite `errorProtocolo()` —con `request_id` nulo— y reporta el código real en lugar de una excepción cruda de JSON.
* **Precondiciones:** Linux o WSL con Bash y Python 3; Hermes compilado; `HOME` temporal con `config.json` que apunta al puerto de la prueba; puerto `45851` libre.
* **Entorno y configuración:** Servidor falso en Python que emite tres sobres consecutivos con `request_id: null` y códigos `MESSAGE_TOO_LARGE`, `REQUEST_TIMEOUT` y `RESPONSE_TOO_LARGE`; el cliente real se invoca como `hermes red job 127.0.0.1 true`.
* **Datos de entrada:** Tres respuestas con el formato exacto `{"version":1,"request_id":null,"ok":false,"error":"<código>"}`.
* **Pasos reproducibles:**
  1. Compilar con `make -C src/hermes hermes`.
  2. Ejecutar `bash verif/scripts/TC-040.sh`.
  3. Revisar el código de salida y `verif/results/results_TC-040.md`.
* **Resultado esperado:** Cada ejecución del cliente termina con código distinto de cero y muestra el código de error recibido. Ninguna salida contiene `json.exception` ni `type_error`. Antes de esta corrección el cliente abortaba con `[json.exception.type_error.302] type must be string, but is null` porque comparaba el `request_id` nulo contra su identificador local.

#### 2. Fase de Ejecución (Resultados empíricos)
* **Resultado observado:** Ejecución del 2026-11-19 en WSL Ubuntu con código `0`. Las tres invocaciones salieron con código `1` y mostraron `MESSAGE_TOO_LARGE`, `REQUEST_TIMEOUT` y `RESPONSE_TOO_LARGE` respectivamente, sin rastro de `json.exception` ni `type_error` en la salida acumulada.
* **Artefactos de evidencia:** `verif/scripts/TC-040.sh`; `verif/results/results_TC-040.md`.
