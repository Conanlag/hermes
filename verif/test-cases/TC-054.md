# TC-054: El plazo de inactividad se renueva por solicitud y sigue vigente

**Requisitos cubiertos:** RNF-24
**Métodos de verificación:** Prueba
**Nivel de prueba:** Funcional y robustez

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Verificar que el plazo de tres segundos se renueva al completar cada solicitud pero no desaparece: una conexión que responde y luego queda inactiva se cierra con `REQUEST_TIMEOUT`, y la bitácora documenta el desenlace de la solicitud atendida.
* **Precondiciones:** Linux o WSL con Bash y Python 3; Hermes compilado; `HOME` temporal aislado; puerto `45860` libre.
* **Entorno y configuración:** `config.json` propio con `puerto: 45860`; `network.json` que autoriza a `PC-B` desde `127.0.0.1`; servidor lanzado por el script.
* **Datos de entrada:** Un `ping` (`tc054-uno`), lectura de su respuesta y `sleep(4.0)` sin enviar nada más sobre la misma conexión.
* **Pasos reproducibles:**
  1. Compilar con `make -C src/hermes hermes`.
  2. Ejecutar `bash verif/scripts/TC-054.sh`.
  3. Revisar el código de salida, `verif/results/results_TC-054.md` y `events.jsonl`.
* **Resultado esperado:** La primera solicitud responde `pong`. Tras la inactividad llega `{"error":"REQUEST_TIMEOUT","request_id":null,...}` y la conexión se cierra. `events.jsonl` contiene un registro `Solicitud interrumpida` con `motivo: TIMEOUT_LECTURA`, `resultado: ACEPTADA` y `request_id: tc054-uno`, sin `Cliente desconectado` para ese motivo. Un `ping` nuevo responde.

#### 2. Fase de Ejecución (Resultados empíricos)
* **Resultado observado:** Ejecución del 2026-11-23 en WSL Ubuntu con código `0`. La primera respuesta fue `pong`; tras `4.0 s` de inactividad llegó `{"error":"REQUEST_TIMEOUT","ok":false,"request_id":null,"version":1}`. La bitácora dejó `{"context": {"bytes_recibidos": 77, "motivo": "TIMEOUT_LECTURA", "operacion": "ping", "request_id": "tc054-uno", "resultado": "ACEPTADA"}, "message": "Solicitud interrumpida", ...}`. El `ping` posterior respondió.
