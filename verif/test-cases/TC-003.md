### TC-003: Estados y tiempos
**Requisitos cubiertos:** RF-06, RF-07
**Nivel de prueba:** Sistema

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Validar que Hermes representa los cinco estados (`QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELED`) con transiciones correctas, y que registra tiempos de recepción, inicio y terminación además del código de salida cuando aplique.
* **Precondiciones:** Repositorio clonado limpio; `src/hermes` compilado con `make clean && make` sin errores; `data/jobs.json` respaldado; reloj del sistema sincronizado para comparar marcas de tiempo.
* **Entorno y configuración:** Linux (WSL), compilador GCC (g++, `-Wall -Wextra -std=c++17 -Iinclude`), entorno controlado, clon limpio, límite de concurrencia definido en config.json.
* **Datos de entrada:** `./hermes job true` (éxito), `./hermes job false` (fallo), `./hermes job sleep 30` + `./hermes cancel` (cancelación); lecturas con `./hermes filter id <N>` e inspección de `data/jobs.json`.
* **Pasos reproducibles:**
  1. Compilar: `cd src/hermes && make clean && make`.
  2. Caso éxito: `./hermes job true`, anotar ID (`A`); esperar 2 s; `./hermes filter id A` y anotar estado y código de salida.
  3. Caso fallo: `./hermes job false`, anotar ID (`B`); esperar 2 s; `./hermes filter id B` y anotar estado y código de salida.
  4. Caso cancelación: `./hermes job sleep 30`, anotar ID (`C`); `./hermes cancel C`; `./hermes filter id C` y anotar estado y código de salida.
  5. Verificar RF-06: comprobar `A = SUCCEEDED`, `B = FAILED`, `C = CANCELED`, y que durante la ventana previa `C` pasó por `QUEUED` y `RUNNING` (repetir con `filter id` inmediato tras crear).
  6. Verificar RF-07: en `data/jobs.json`, para cada ID comprobar `codigo_salida` (`0` en éxito, distinto de `0` en fallo, `-SIGTERM` en cancelado) y la presencia de marcas de recepción, inicio y terminación con orden cronológico coherente (recepción ≤ inicio ≤ terminación).
* **Resultado esperado:** Paso 5 muestra los cinco estados representados con transiciones `QUEUED → RUNNING → (SUCCEEDED | FAILED | CANCELED)`; paso 6 muestra `codigo_salida` correcto por caso y las tres marcas de tiempo presentes, con formato consistente y orden válido. Ausencia de marcas o estados fuera del vocabulario se registra como defecto.

#### 2. Fase de Ejecución (Resultados empíricos)
* **Resultado observado:** El script `TC-003.sh` validó con éxito los pasos 1, 2, 3, 4 y 6. Los estados `RUNNING`, `SUCCEEDED`, `FAILED` y `CANCELED` funcionan perfectamente, asignando los códigos correctos (`0`, `1`, `-15` por SIGTERM) y registrando la cronología exacta. El único fallo ocurre en el Paso 5: el sistema omite el estado `QUEUED` pasando a `RUNNING` de forma inmediata. Este comportamiento es esperado para el Hito 1, ya que la lógica de retención de trabajos en cola (concurrencia) pertenece al alcance del Hito 2.
* **Nota Técnica de QA:** Durante las pruebas automatizadas tempranas, iteraciones previas del script en bash generaban un falso defecto donde los trabajos en segundo plano (`sleep 30`) terminaban instantáneamente en `SUCCEEDED`. El análisis de QA determinó que la causa raíz no era el código C++, sino la gestión de tuberías en bash (uso de `| grep`) en el script. Al cerrarse la lectura de la tubería, Linux enviaba una señal `SIGPIPE`, asesinando el proceso en segundo plano de manera prematura. El script final se corrigió redirigiendo la salida a archivos temporales (`> /tmp/`), confirmando que la lógica del ejecutable es sólida e intacta.
