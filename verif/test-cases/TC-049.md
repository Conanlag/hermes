# TC-049: Mensaje fragmentado que supera el plazo anterior

**Requisitos cubiertos:** RNF-24
**Métodos de verificación:** Prueba
**Nivel de prueba:** Funcional y robustez

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Verificar que un mensaje que llega byte a byte durante más de tres segundos se acumula hasta el delimitador y se atiende: el plazo de lectura mide inactividad, no tiempo desde `accept`.
* **Precondiciones:** Linux o WSL con Bash y Python 3; Hermes compilado; `HOME` temporal aislado; puerto `45855` libre.
* **Entorno y configuración:** `config.json` propio con `puerto: 45855`; `network.json` que autoriza a `PC-B` desde `127.0.0.1` con `submit` habilitado; servidor lanzado por el script.
* **Datos de entrada:** Un `submit` válido (`tc049-fragmentado`) enviado en 123 escrituras de un byte, con 40 ms entre cada una; el envío completo dura unos 4,9 s.
* **Pasos reproducibles:**
  1. Compilar con `make -C src/hermes hermes`.
  2. Ejecutar `bash verif/scripts/TC-049.sh`.
  3. Revisar el código de salida y `verif/results/results_TC-049.md`.
* **Resultado esperado:** El servidor responde `ok: true` con `request_id: tc049-fragmentado`. `jobs.json` contiene exactamente un Job. El envío medido supera los tres segundos y el `ping` posterior responde.

#### 2. Fase de Ejecución (Resultados empíricos)
* **Resultado observado:** Ejecución del 2026-11-22 en WSL Ubuntu con código `0`. El envío fragmentado tardó `4.96 s`; la respuesta fue `{"ok": true, "request_id": "tc049-fragmentado", ... "job_id": 1}`; `jobs.json` contenía `1` Job con `request_id` `red-tcp-PC-B-tc049-fragmentado`; el `ping` posterior respondió correctamente.
* **Artefactos de evidencia:** `verif/scripts/TC-049.sh`; `verif/results/results_TC-049.md`.
