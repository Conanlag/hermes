### [TC-020]: Terminación inesperada del proceso hijo
**Requisitos cubiertos:** RF-29, RNF-30  
**Métodos de verificación:** Prueba  
**Nivel de prueba:** Robustez

#### 1. Fase de Diseño (Planificación)

- **Objetivo:** Verificar que el motor Hermes detecte de forma inmediata y determinista la muerte anormal de un proceso hijo (causada por señales fatales del sistema operativo), libere sus recursos asociados (descriptores de archivos y tabla de procesos vía `waitpid`), y evite la generación de procesos huérfanos o zombies aislando la ejecución mediante grupos de procesos (`setpgid`). Adicionalmente, comprobar que el sistema persiste el estado terminal `FAILED` acompañado de un diagnóstico forense detallado en `jobs.json` y `events.jsonl`.

- **Precondiciones:** 
  1. Repositorio clonado limpio.
  2. Proyecto compilado con `make` en un entorno Linux/WSL.
  3. Directorio de datos `$HOME/.local/share/hermes/data/` accesible con permisos para crear/leer `jobs.json` y `events.jsonl`.
  4. Sin instancias activas del scheduler o comandos `hermes` en ejecución que puedan interferir con la prueba.
  5. Límite de concurrencia definido en `config.json`.

- **Entorno y configuración:** 
  - SO: Linux (WSL)
  - Compilador: GCC/Clang
  - Entorno controlado y clon limpio
  - Gestión de grupos de procesos (`setpgid`, `kill(-pgid)`)
  - Aislamiento POSIX (`_GNU_SOURCE` para `strsignal`)

- **Datos de entrada:**
  1. Invocación de un trabajo diseñado explícitamente para auto-terminarse mediante una violación de segmento: `hermes job bash -c "kill -SEGV \$\$"`
  2. (Opcional para verificación complementaria): Invocación de un trabajo de larga duración (`hermes job sleep 100`) que será asesinado de forma externa enviando un `SIGKILL` directamente a su PID o PGID.

- **Pasos reproducibles:** 
  1. **Preparación:** Inicializar el entorno limpiando o vaciando los archivos `jobs.json` y `events.jsonl`.
  2. **Ejecución:** Encolar el comando que provocará el crash del sistema: `hermes job bash -c "kill -SEGV \$\$"`.
  3. **Espera:** Esperar 2 segundos para permitir que el scheduler asigne el trabajo, realice el `fork`, establezca el PGID y el proceso hijo muera prematuramente.
  4. **Consulta:** Ejecutar `hermes filter id <jobId>` para recuperar el estado visible por el usuario.
  5. **Verificación de Persistencia:** Inspeccionar el archivo `jobs.json` buscando el objeto correspondiente al trabajo.
  6. **Verificación de Auditoría:** Inspeccionar el archivo `events.jsonl` buscando el log asociado a la transición de estado del trabajo.
  7. **Verificación de Huérfanos/Zombies:** Ejecutar una consulta a nivel de sistema operativo (`ps -p <PID>` o `ps -j`) comprobando que ni el proceso hijo ni su grupo de procesos persisten en estado `<defunct>`.

- **Resultado esperado:** 
  1. El comando de consulta en la CLI devuelve el estado `FAILED`, reporta un código de salida numérico negativo (ej. `-11` para `SIGSEGV`) y exhibe el "Mensaje de error" detallando la señal fatal y su descripción (ej. `Terminado por señal fatal SIGSEGV (11): Segmentation fault`).
  2. El archivo `jobs.json` registra correctamente el cambio a estado `FAILED`, mapeando el código numérico negativo y los tiempos de ejecución.
  3. El archivo `events.jsonl` contiene una entrada de nivel `ERROR` con los metadatos de contexto validados: `anomalous_termination: true`, el `signal_number`, y el `signal_name`.
  4. El sistema operativo confirma que los recursos fueron liberados (cierre de tubería `stderr` e invocación correcta de `waitpid`), asegurando que no existan procesos huérfanos ni zombies atados al scheduler.

#### 2. Fase de Ejecución (Resultados empíricos)
- **Resultado observado:** Se encoló un Job suicida (bash -c 'kill -SEGV $$'). El servicio Hermes detectó determinísticamente la terminación anormal por señal fatal SIGSEGV (11), cosechando al proceso subordinado mediante waitpid y cerrando la tubería stderr. Se registró la transición a estado FAILED con código de salida -11 y la salida de diagnóstico en la CLI (Terminado por señal fatal SIGSEGV (11): Segmentation fault). Se validó la persistencia atómica en jobs.json, el registro forense en events.jsonl (anomalous_termination: true, signal_number: 11) y la ausencia de procesos zombies (<defunct>) o huérfanos en la tabla de procesos del sistema operativo.
