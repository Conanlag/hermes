# Gestión de Jobs — RF-01

## Objetivo

El módulo `job` implementa la funcionalidad correspondiente al **RF-01** de Hermes:

> El sistema deberá aceptar el envío de un comando o programa con sus argumentos y devolver un identificador único de trabajo.

La implementación permite recibir un programa junto con sus argumentos, crear un `Job`, asignarle un identificador único, crear un proceso real de Linux y ejecutar el programa solicitado.

Los Jobs son persistidos en un archivo JSON para conservar su información entre diferentes ejecuciones de Hermes.

Además, el proceso creado se ejecuta de forma independiente al proceso principal de Hermes, permitiendo que el comando `hermes job` devuelva el control de la terminal inmediatamente.

# Dependencia nlohmann/json

Hermes utiliza la biblioteca **nlohmann/json v3.12.0** para leer y escribir la información de los Jobs en formato JSON.

La biblioteca es de tipo **header-only**, por lo que no requiere enlazar una biblioteca adicional durante la compilación.

El archivo utilizado es:

```text
include/nlohmann/json.hpp
```

La dependencia se encuentra directamente dentro del repositorio de Hermes para evitar depender de una instalación global en el sistema.

Por lo tanto, no es necesario instalarla mediante el administrador de paquetes del sistema:

```bash
sudo apt install nlohmann-json3-dev
```

La compilación utiliza directamente la versión almacenada en el proyecto.

## Inclusión en C++

Los archivos que utilizan la biblioteca pueden incluirla mediante:

```cpp
#include <nlohmann/json.hpp>

using json = nlohmann::json;
```

## Integración con Makefile

El `Makefile` agrega el directorio `include` como ruta de búsqueda para los archivos de cabecera:

```make
CXXFLAGS = -Wall -Wextra -std=c++17 -Iinclude
```

La opción:

```text
-Iinclude
```

permite que el compilador encuentre:

```text
include/nlohmann/json.hpp
```

No es necesario utilizar:

```text
-ljson
```

debido a que `nlohmann/json` es una biblioteca *header-only*.

# `job.h`

## Propósito

El archivo `job.h` contiene la definición de la estructura que representa un trabajo dentro de Hermes.

También declara la función encargada de crear un nuevo Job.

## Dependencias

```cpp
#include <string>
#include <vector>
#include "status.h"
```

Se utilizan:

* `std::string` para almacenar el nombre del programa.
* `std::vector<std::string>` para almacenar sus argumentos.
* `Status` para representar el estado del Job.

## Estructura `Job`

La estructura contiene actualmente:

```cpp
struct Job {
    unsigned int job_id;
    int pid;
    string programa;
    vector<string> argumentos;
    Status status;
};
```

### `job_id`

```cpp
unsigned int job_id;
```

Identificador del trabajo.

Este valor permite distinguir un Job de otro y es generado consultando los Jobs existentes en `data/jobs.json`.

### `pid`

```cpp
int pid;
```

Identificador del proceso asignado por Linux.

A diferencia de `job_id`, que pertenece a Hermes, el `PID` corresponde al proceso real creado por el sistema operativo.

Por ejemplo:

```text
Job ID: 8
PID: 5240
```

### `programa`

```cpp
string programa;
```

Contiene el nombre o comando recibido por Hermes.

Ejemplo:

```text
ls
```

### `argumentos`

```cpp
vector<string> argumentos;
```

Contiene los argumentos asociados al programa.

Por ejemplo:

```bash
hermes job ls -la /tmp
```

se almacena como:

```text
programa = "ls"

argumentos:
    "-la"
    "/tmp"
```

### `status`

```cpp
Status status;
```

Representa el estado actual del Job.

Los estados definidos por Hermes son:

```text
QUEUED
RUNNING
SUCCEEDED
FAILED
CANCELED
```

---

# Función `crearJob()`

La función se declara como:

```cpp
Job crearJob(
    const string& programa,
    const vector<string>& argumentos
);
```

Recibe:

1. El programa.
2. Los argumentos del programa.

Y devuelve:

```cpp
Job
```

con un identificador asignado, el PID del proceso creado y la información correspondiente.

Además de crear el objeto en memoria, la implementación persiste el nuevo Job en:

```text
data/jobs.json
```

---

# `job.cpp`

## Propósito

`job.cpp` contiene la implementación de `crearJob()`.

Su responsabilidad actual es:

1. Leer los Jobs existentes desde `data/jobs.json`.
2. Determinar el siguiente `job_id`.
3. Crear un proceso mediante `fork()`.
4. Crear un `Job`.
5. Asignar el ID.
6. Asociar el PID.
7. Guardar el programa.
8. Guardar los argumentos.
9. Asignar el estado correspondiente.
10. Ejecutar el programa mediante `execvp()`.
11. Agregar el nuevo Job al arreglo JSON.
12. Persistir nuevamente la información en `data/jobs.json`.
13. Devolver el Job.

---

# Archivo JSON

La persistencia se realiza mediante:

```cpp
const string archivoJobs = "data/jobs.json";
```

Este archivo contiene un arreglo JSON con los Jobs creados.

Ejemplo:

```json
[
    {
        "job_id": 1,
        "pid": 5240,
        "programa": "sleep",
        "argumentos": [
            "120"
        ],
        "status": "RUNNING"
    },
    {
        "job_id": 2,
        "pid": 5300,
        "programa": "echo",
        "argumentos": [
            "Hola"
        ],
        "status": "RUNNING"
    }
]
```

Cada elemento del arreglo representa un Job.

---

# Lectura de los Jobs existentes

Antes de crear un nuevo Job, `crearJob()` intenta abrir:

```text
data/jobs.json
```

mediante:

```cpp
ifstream archivoLectura(archivoJobs);
```

Si el archivo existe, su contenido se carga en un objeto JSON:

```cpp
json jobs = json::array();

if (archivoLectura.is_open()) {
    try {
        archivoLectura >> jobs;
    } catch (const json::parse_error&) {
        jobs = json::array();
    }

    archivoLectura.close();
}
```

Inicialmente se establece como un arreglo vacío:

```cpp
json::array()
```

Esto permite que Hermes pueda comenzar a crear Jobs aunque todavía no exista información almacenada.

---

# Generación del `job_id`

El siguiente identificador se obtiene recorriendo los Jobs existentes:

```cpp
unsigned int siguienteId = 1;

for (const auto& job : jobs) {
    if (job.contains("job_id") &&
        job["job_id"].is_number_unsigned()) {

        unsigned int id = job["job_id"];

        if (id >= siguienteId) {
            siguienteId = id + 1;
        }
    }
}
```

El valor inicial es:

```text
1
```

Si no existen Jobs:

```text
job_id = 1
```

Si el archivo contiene Jobs con IDs:

```text
1
2
3
```

el siguiente identificador será:

```text
4
```

## Búsqueda del ID máximo

El algoritmo no depende únicamente de la cantidad de elementos del arreglo.

Por ejemplo, si el archivo contiene:

```json
[
    {
        "job_id": 1
    },
    {
        "job_id": 5
    }
]
```

el siguiente identificador será:

```text
6
```

Esto se debe a que `crearJob()` busca el identificador más alto almacenado y utiliza el siguiente valor.

---

# Creación del proceso

Después de obtener el identificador, Hermes crea un proceso mediante:

```cpp
pid_t pid = fork();
```

`fork()` permite crear un nuevo proceso a partir del proceso actual.

El valor retornado permite distinguir entre el proceso padre y el proceso hijo.

```text
fork()
  │
  ├── pid < 0 → error
  │
  ├── pid == 0 → proceso hijo
  │
  └── pid > 0 → proceso padre
```

---

# Proceso hijo

Cuando:

```cpp
pid == 0
```

Hermes se encuentra dentro del proceso hijo.

Este proceso es el encargado de ejecutar el programa solicitado.

Primero se construye el arreglo de argumentos:

```cpp
vector<char*> argumentosExec;

argumentosExec.push_back(
    const_cast<char*>(programa.c_str())
);

for (const auto& argumento : argumentos) {
    argumentosExec.push_back(
        const_cast<char*>(argumento.c_str())
    );
}

argumentosExec.push_back(nullptr);
```

El arreglo termina con `nullptr` porque es el formato esperado por `execvp()`.

Posteriormente se ejecuta:

```cpp
execvp(
    programa.c_str(),
    argumentosExec.data()
);
```

---

# Ejecución mediante `execvp()`

`execvp()` reemplaza la imagen del proceso hijo por el programa solicitado.

Por ejemplo:

```bash
hermes job sleep 120
```

produce conceptualmente:

```text
Hermes
   │
   └── fork()
         │
         └── proceso hijo
                │
                └── execvp()
                       │
                       └── sleep 120
```

De esta manera, Hermes puede ejecutar programas reales disponibles para el usuario.

---

# Proceso padre

El proceso padre recibe el PID del proceso hijo:

```cpp
pid_t pid = fork();
```

Cuando:

```cpp
pid > 0
```

el valor representa el PID del proceso hijo.

El PID se almacena dentro del Job:

```cpp
job.pid = pid;
```

Esto permite relacionar:

```text
Job de Hermes
       │
       └── PID de Linux
```

Por ejemplo:

```text
Job ID: 8
PID: 5240
Programa: sleep
```

---

# Ejecución en segundo plano

El proceso padre **no espera a que termine el proceso hijo** durante la creación del Job.

Por lo tanto:

```bash
hermes job sleep 120
```

devuelve inmediatamente:

```text
job ID: 8
PID: 5240
```

y la terminal vuelve a estar disponible:

```text
leo@NOVI:~/proyecto/ppl/src/hermes$
```

Mientras tanto, el proceso continúa ejecutándose:

```text
Hermes
   │
   └── sleep 120
          │
          └── continúa ejecutándose
```

Esto permite que Hermes funcione como administrador de Jobs sin bloquear la terminal durante la ejecución del programa.

---

# Creación del Job

Una vez obtenido el PID, se crea el objeto:

```cpp
Job job;
```

Posteriormente se asignan sus datos:

```cpp
job.job_id = siguienteId;
job.pid = pid;
job.programa = programa;
job.argumentos = argumentos;
job.status = Status::RUNNING;
```

Por ejemplo:

```bash
hermes job sleep 120
```

produce conceptualmente:

```text
Job
├── job_id: 8
├── pid: 5240
├── programa: "sleep"
├── argumentos:
│   └── "120"
└── status: RUNNING
```

---

# Conversión del Job a JSON

Después de crear el `Job`, se genera su representación JSON:

```cpp
json nuevoJob;

nuevoJob["job_id"] = job.job_id;
nuevoJob["pid"] = job.pid;
nuevoJob["programa"] = job.programa;
nuevoJob["argumentos"] = job.argumentos;
nuevoJob["status"] = statusToString(job.status);
```

El resultado es conceptualmente:

```json
{
    "job_id": 8,
    "pid": 5240,
    "programa": "sleep",
    "argumentos": [
        "120"
    ],
    "status": "RUNNING"
}
```

Este objeto posteriormente se agrega al arreglo:

```cpp
jobs.push_back(nuevoJob);
```

---

# Persistencia del Job

Después de agregar el nuevo Job al arreglo, se abre el archivo para escritura:

```cpp
ofstream archivoEscritura(archivoJobs);
```

El arreglo completo se escribe nuevamente:

```cpp
archivoEscritura << jobs.dump(4);
```

El parámetro:

```text
4
```

indica el nivel de indentación utilizado para generar un JSON legible.

Hermes ya no utiliza:


para almacenar el siguiente identificador.

La implementación actual obtiene el identificador directamente de:

```text

```

Esto permite que el archivo JSON funcione como:

* almacenamiento de los Jobs;
* fuente para determinar el siguiente identificador.

# Persistencia

La utilización de `jobs.json` permite conservar la información de los Jobs después de que termina el proceso de Hermes.

Por ejemplo:

```bash
hermes job sleep 120
```

puede producir:

```text
Job ID: 8
PID: 5240
```

Posteriormente, la información permanece almacenada en:

```text
data/jobs.json
```

aunque la ejecución del comando `hermes` haya terminado.

# Verificación de procesos

Los procesos creados por Hermes pueden verificarse directamente mediante herramientas de Linux.

Después de ejecutar:

```bash
hermes job sleep 120
```

y obtener:

```text
Job ID: 8
PID: 5240
```

puede ejecutarse:

```bash
ps -fp 5240
```

Resultado:

```text
UID   PID   PPID  C STIME TTY          TIME CMD
leo   5240  466   0 22:27 pts/4    00:00:00 sleep 120
```

Esto demuestra que el proceso:

* existe realmente en Linux;
* pertenece al usuario que ejecutó Hermes;
* continúa ejecutándose después de que Hermes devuelve el control de la terminal;
* corresponde al programa solicitado.

También puede utilizarse:

```bash
pgrep -a sleep
```


```text

PID: 5240
```

Posteriormente:

```bash
hermes job sleep 60
```


Ambos procesos pueden permanecer activos simultáneamente.

```text
PID 5240 → sleep 120
PID 5941 → sleep 60
```

## Prueba 3 — `echo`

```bash
hermes job echo hola
```

Resultado:

```text
job ID: 10
PID: 6084
hola
```

El proceso termina prácticamente de inmediato debido a la naturaleza del comando `echo`.

Por esta razón, si posteriormente se ejecuta:

```bash
ps -fp 6084
```

es posible que el proceso ya no aparezca.

Esto no representa un error: significa que el programa ya terminó.

## Prueba 4 — `ping`

```bash

```

El proceso ejecuta el programa real:

```text

```

y completa las cinco solicitudes.

Esta prueba permite verificar que Hermes puede ejecutar un programa real junto con múltiples argumentos.

# Ejecución sin `sudo`

La creación de procesos realizada por Hermes no requiere privilegios de administrador.

Los procesos son ejecutados con los permisos del usuario que ejecuta Hermes.

Por ejemplo:

```text
UID: leo
```

Esto puede verificarse mediante:

```bash
ps -fp <PID>
```

No es necesario utilizar:

```bash
sudo hermes ...
```

para crear y ejecutar los Jobs normales del usuario.

---

# Relación entre `job_id` y PID

Hermes maneja dos identificadores diferentes:

```text
Job ID
```

identifica el trabajo dentro de Hermes.

```text
PID
```

identifica el proceso dentro de Linux.

Por ejemplo:

```text
Job ID: 8
PID: 5240
```

La relación puede representarse como:

```text
Hermes
 │
 └── Job 8
       │
       ├── programa: sleep
       ├── argumentos: 120
       └── PID: 5240
                    │
                    ↓
                Linux
                    │
                    └── sleep 120
```

# Consideraciones actuales

Esta implementación corresponde a una etapa más avanzada de RF-01.

Actualmente:

* Los Jobs se almacenan en `data/jobs.json`.
* Los identificadores se obtienen a partir de los Jobs existentes.
* Los programas recibidos **sí se ejecutan** como procesos reales.
* Los procesos se crean mediante `fork()`.
* Los programas se ejecutan mediante `execvp()`.
* Cada proceso obtiene un PID real de Linux.
* El PID se almacena junto con el Job.
* Los procesos se ejecutan sin necesidad de `sudo`.
* Hermes devuelve el control de la terminal inmediatamente.
* Se pueden ejecutar múltiples Jobs simultáneamente.
* Los argumentos del programa se conservan y se pasan al proceso.
* `stdout` y `stderr` todavía utilizan los descriptores heredados del proceso padre.
* Todavía no existe seguimiento completo de la terminación del proceso.
* Todavía no se actualizan automáticamente los estados `SUCCEEDED` y `FAILED`.
* Todavía no existe una implementación completa de cancelación.
* Todavía no existe persistencia mediante SQLite.
* Todavía no existe recuperación de procesos después de reiniciar Hermes.
* Todavía no existe comunicación remota.
