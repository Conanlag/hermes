# RF-29 — Manejo de terminación inesperada de procesos hijo

## Descripción

En entornos de ejecución basados en procesos POSIX, los procesos hijo ejecutados por un despachador pueden ser terminados de forma anormal debido a señales fatales del sistema operativo (`SIGSEGV`, `SIGFPE`, `SIGILL`, `SIGBUS`), por intervención externa de administradores u otros servicios (`SIGKILL`, `SIGTERM`), o por decisiones de gestión de memoria del kernel (`OOM Killer`).

El requisito funcional RF-29 define la arquitectura mediante la cual el servicio Hermes supervisa la vida de los procesos hijo, detecta de forma determinista y sin latencia su terminación inesperada, libera inmediatamente todos los recursos asociados (descriptores de archivos de pipes de `stderr` y entradas en la tabla de procesos del sistema operativo) y persiste un estado terminal `FAILED` acompañado de metadatos de diagnóstico forense.

Esta solución garantiza que ante una caída imprevista del proceso hijo, el sistema preserve la integridad de la base de datos de trabajos (`jobs.json`), evite la creación de procesos zombies, no contamine otros trabajos en ejecución y provea trazabilidad completa en la bitácora operativa (`events.jsonl`) y en la interfaz de línea de comandos (CLI).

---

## Objetivo

Garantizar la resiliencia y observabilidad del servicio Hermes ante la muerte abrupta de procesos subordinados, evitando fugas de recursos del sistema operativo y registrando información diagnóstica precisa sobre la causa del fallo.

> *"Si un proceso hijo termina inesperadamente, el servicio deberá detectar el evento, liberar sus recursos y registrar un estado terminal con información de diagnóstico."*

**Consideraciones actuales:**
- **Lo que hace:**
  - Evalúa rigurosamente las macros POSIX `WIFEXITED`, `WIFSIGNALED`, `WTERMSIG` y `WCOREDUMP` en `process.cpp`.
  - Mapea el número de señal a su nombre canónico (`SIGSEGV`, `SIGKILL`, `SIGABRT`, etc.) y a su descripción legible (`strsignal`), normalizando a `"señal desconocida"` si esta no está disponible. Se define `#define _GNU_SOURCE` en `process.cpp` para garantizar la visibilidad de `strsignal` en glibc/Linux (WSL).
  - Detecta la terminación mediante el cierre natural del descriptor de escritura del pipe de `stderr` por parte del kernel (`read == 0` en el hilo trabajador).
  - Cosecha de inmediato al proceso hijo con `waitpid` sincrónico en el hilo de trabajo, liberando la tabla de procesos del SO sin riesgo de zombies.
  - Libera y garantiza el cierre seguro de los descriptores de lectura (`pipeStderr`) comprobando `pipeStderr >= 0` antes de `close()` en rutas normales y excepcionales.
  - Persiste el estado `FAILED`, el código de salida negativo correspondiente (`-numeroSenal`) y un diagnóstico detallado en el campo `mensaje_error` de `jobs.json`.
  - Registra un evento de nivel `ERROR` en `events.jsonl` con el contexto diagnóstico enriquecido (`exit_code`, `signal_number`, `signal_name`, `signal_description`, `core_dump`, `anomalous_termination`). Cuando la terminación es por señal, `anomalous_termination: true`. Cuando el proceso sale normalmente con código distinto a `0`, `anomalous_termination: false`.
  - Muestra el diagnóstico textual en the CLI a través de `hermes filter id <job_id>`.
- **Lo que NO hace:**
  - No reinicia ni reintenta automáticamente los trabajos que fallaron por crash (la política de fallos es terminal y no recuperable automáticamente).
  - No intercepta `SIGCHLD` de forma asíncrona global para evitar condiciones de carrera en multihilo.
  - No analiza ni almacena archivos físicos de volcado de memoria (`core dumps` en `/var/lib/systemd/coredump` o directorio de trabajo).
  - No altera el comportamiento de las cancelaciones voluntarias solicitadas por el usuario (`CANCELED`), las cuales se discriminan limpiamente.

## Definición de los estados

El RF-29 interactúa directamente con los estados terminales del ciclo de vida del Job:

| Transición | Condición Desencadenante | Estado Resultante | Código de Salida | Diagnóstico Asociado |
|---|---|---|---|---|
| `RUNNING -> FAILED` | Muerte anormal por señal del SO (`WIFSIGNALED`) sin solicitud de cancelación previa. | `FAILED` | `-numeroSenal` (ej. `-11`) | Nombre de señal, código numérico, descripción textual y si hubo volcado de memoria (*core dump*). |
| `RUNNING -> FAILED` | Proceso sale con código de retorno de error (`WIFEXITED && status != 0`). | `FAILED` | `WEXITSTATUS` (ej. `1`, `127`) | Mensaje `"El proceso terminó con código de error N"`. |
| `RUNNING -> CANCELED` | Muerte del proceso tras una cancelación solicitada explícitamente (`cancel_requested == true`). | `CANCELED` | Código de la señal (`-15` o `-9`) | Se cataloga como cancelación exitosa (Nivel `INFO`), no como caída anormal. |
| `RUNNING -> SUCCEEDED` | El proceso finaliza de forma limpia y exitosa (`WIFEXITED && status == 0`). | `SUCCEEDED` | `0` | Sin mensaje de error. |

#### 2. Detección y Recolección en `esperarProceso`
La función encapsula el llamado a `waitpid`, manejando interrupciones por señales (`EINTR`) y extrayendo de forma segura las macros del sistema:

```cpp
bool esperarProceso(pid_t pid, ResultadoProceso& resultado) {
    resultado = ResultadoProceso{};
    int estado = 0;

    while (true) {
        pid_t res = waitpid(pid, &estado, 0);

        if (res == -1) {
            if (errno == EINTR) {
                continue;
            }

            resultado.completado = false;
            resultado.codigoSalida = -1;
            return false;
        }

        break;
    }

    resultado.completado = true;

    if (WIFEXITED(estado)) {
        resultado.salidoNormalmente = true;
        resultado.codigoSalida = WEXITSTATUS(estado);
        return true;
    }

    if (WIFSIGNALED(estado)) {
        resultado.terminadoPorSenal = true;
        resultado.numeroSenal = WTERMSIG(estado);
        resultado.codigoSalida = -resultado.numeroSenal;
        resultado.nombreSenal = obtenerNombreSenal(resultado.numeroSenal);
        const char* desc = strsignal(resultado.numeroSenal);
        resultado.descripcionSenal = (desc != nullptr && desc[0] != '\0') ? desc : "señal desconocida";
#ifdef WCOREDUMP
        resultado.coreDump = WCOREDUMP(estado);
#endif
        return true;
    }

    resultado.codigoSalida = -1;
    return false;
}
```

### `src/scheduler/scheduler.cpp`

#### 1. Supervisión en el Hilo Trabajador y Cierre de Pipes
El hilo trabajador aprovecha el cierre del extremo de escritura del pipe de `stderr` por parte del kernel como mecanismo de desbloqueo reactivo (latencia cero, sin polling):

```cpp
// Consumir stderr hasta EOF (cuando el proceso hijo muere)
char buffer[512];
while (true) {
    ssize_t n = read(pipeStderr, buffer, sizeof(buffer));
    if (n == 0) break;
    if (n < 0) {
        if (errno == EINTR) continue;
        break;
    }
}

if (pipeStderr >= 0) {
    close(pipeStderr);
    pipeStderr = -1;
}

ResultadoProceso resultado;
esperarProceso(pid, resultado);

const bool interrumpido = desregistrarTrabajoActivo(trabajo.id);
procesoRegistrado = false;

if (interrumpido) {
    return;
}

finalizarTrabajo(trabajo.id, resultado);
```

#### 2. Persistencia y Diagnóstico en `finalizarTrabajo`
Cuando se confirma una muerte por señal fatal, se genera el mensaje de error explicativo y se escribe atómicamente en `jobs.json` y `events.jsonl`:

```cpp
void finalizarTrabajo(unsigned int id, const ResultadoProceso& resultado) {
    bool fueCancelado = false;
    bool fueExitoso = false;
    bool fueFallido = false;
    string mensajeDiagnostico;

    if (resultado.terminadoPorSenal) {
        string desc = resultado.descripcionSenal.empty() ? "señal desconocida" : resultado.descripcionSenal;
        mensajeDiagnostico = "Terminado por señal fatal " +
            resultado.nombreSenal + " (" +
            to_string(resultado.numeroSenal) + "): " +
            desc +
            (resultado.coreDump ? " (core dumped)" : "");
    } else if (!resultado.salidoNormalmente && !resultado.completado) {
        mensajeDiagnostico = "Error al esperar la terminación del proceso";
    } else if (resultado.codigoSalida != 0) {
        mensajeDiagnostico = "El proceso terminó con código de error " +
            to_string(resultado.codigoSalida);
    }

    modificarJobsSeguros([&](json& jobs) {
        for (auto& item : jobs) {
            if (!item.contains("job_id") || item["job_id"] != id) {
                continue;
            }

            bool cancelar = item.contains("cancel_requested") &&
                            item["cancel_requested"].is_boolean() &&
                            item["cancel_requested"].get<bool>();

            if (cancelar) {
                item["status"] = "CANCELED";
                fueCancelado = true;
            } else if (resultado.salidoNormalmente && resultado.codigoSalida == 0) {
                item["status"] = "SUCCEEDED";
                fueExitoso = true;
            } else {
                item["status"] = "FAILED";
                fueFallido = true;
                if (!mensajeDiagnostico.empty()) {
                    item["mensaje_error"] = mensajeDiagnostico;
                }
            }

            item["codigo_salida"] = resultado.codigoSalida;
            item["tiempo_terminacion"] = obtenerFechaHoraActual();
            return true;
        }
        return false;
    });

    if (fueFallido) {
        nlohmann::json ctx;
        ctx["exit_code"] = resultado.codigoSalida;
        if (resultado.terminadoPorSenal) {
            ctx["signal_number"] = resultado.numeroSenal;
            ctx["signal_name"] = resultado.nombreSenal;
            if (!resultado.descripcionSenal.empty()) {
                ctx["signal_description"] = resultado.descripcionSenal;
            }
            ctx["core_dump"] = resultado.coreDump;
            ctx["anomalous_termination"] = true;
        } else {
            ctx["anomalous_termination"] = false;
        }
        if (!mensajeDiagnostico.empty()) {
            ctx["detalle"] = mensajeDiagnostico;
        }
        hermes::EventLog::log_event(id, hermes::EventLevel::ERROR, "Transición a FAILED", ctx);
    }
}
```

## Integración con otros Requisitos Funcionales

- **RF-06 (Consulta de estado):** Provee el valor `FAILED` y su correspondiente código de retorno negativo a la interfaz de usuario.
- **RF-10 (Cancelación) y RF-30 (Escalamiento de cancelación):** Mantiene la discriminación semántica: si el proceso termina por `SIGTERM` o `SIGKILL` pero tiene la bandera `cancel_requested`, el estado final es `CANCELED` (evento `INFO`), no un fallo de ejecución.
- **RF-11 (Redirección de stderr):** La tubería de error estándar se vacía y se cierra inmediatamente después del crash, liberando el descriptor en el daemon.
- **RF-14 (Bitácora de eventos y errores):** Alimenta el archivo `events.jsonl` con un registro de nivel `ERROR` que incluye en su nodo `context` las claves `exit_code`, `signal_number`, `signal_name`, `signal_description`, `core_dump` y `anomalous_termination` (`true` si es por señal, `false` si es por código de salida distinto a 0), además de `detalle` cuando aplica.
- **RNF-09 (Aislamiento de fallos):** Garantiza que el crash de un hijo no arrastre al hilo supervisor ni a otros trabajos en curso, preservando la estabilidad del motor.
