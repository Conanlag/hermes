# TC-030: Desconexión abrupta del cliente (FIN, RST y SIGKILL)

**Requisitos cubiertos:** RF-22 (AC1, AC2, AC3, AC4)
**Métodos de verificación:** Prueba
**Nivel de prueba:** Robustez

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Verificar que una desconexión del cliente —FIN tras un `submit`, RST tras un `submit` o `SIGKILL` durante un mensaje parcial— no termina el servicio, no deja Jobs parciales en `jobs.json` y permite que los Jobs aceptados alcancen estado terminal.
* **Precondiciones:** Linux o WSL con Bash y Python 3; Hermes compilado; `~/.local/share/hermes/network/network.json` escribible; puerto `45820` libre.
* **Entorno y configuración:** `HOME` temporal aislado; `network.json` registra `127.0.0.1` con permisos `submit/query/list/cancel` y programas `true/sleep/echo/ls`; el script arranca `hermes red start` en segundo plano y lo detiene al final.
* **Datos de entrada:** Tres solicitudes `submit` con `programa: "true"` y sin argumentos, cada una cortada de forma distinta.
* **Pasos reproducibles:**
  1. Compilar con `make -C src/hermes`.
  2. Ejecutar `bash verif/scripts/TC-030.sh`.
  3. Revisar el código de salida y `verif/results/results_TC-030.md`.
* **Resultado esperado:** El script termina con código `0`; tras cada corte el proceso servidor sigue vivo, responde `ping` con `pong`, `jobs.json` sigue siendo un arreglo válido con Jobs completos y los Jobs aceptados llegan a estado terminal.

#### 2. Fase de Ejecución (Resultados empíricos)
* **Resultado observado:** Ejecución del 2026-11-18 en WSL Ubuntu con código `0`. Los tres escenarios (V1 FIN, V2 RST, V3 `SIGKILL` con mensaje parcial) terminaron con `PASS`; el servicio respondió `ping` después de cada corte y los Jobs aceptados alcanzaron estado terminal.
* **Artefactos de evidencia:** `verif/scripts/TC-030.sh`; `verif/results/results_TC-030.md`.
