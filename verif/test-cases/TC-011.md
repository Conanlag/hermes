# TC-011: Restricción de red

**Requisitos cubiertos:** RF-20, RNF-12 y RNF-13.
**Métodos de verificación:** Prueba de integración y revisión de configuración.
**Nivel de prueba:** Funcional, seguridad y robustez.
**Modo:** local, autocontenido en Linux/WSL.

#### 1. Fase de Diseño (Planificación)

* **Objetivo:** Verificar la escucha segura por defecto y la aplicación de reglas IPv4/CIDR al origen TCP observado, incluyendo rechazo sin respuesta, continuidad del servicio y cierre ordenado.
* **Precondiciones:** Hermes compilado; Bash, Python 3, `ss`, `mktemp` y `tee`; acceso a `/proc`; usuario sin privilegios y permiso para crear sockets de loopback. El entorno debe permitir enlazar los orígenes `127.0.0.1`, `127.0.0.2` y `127.0.0.5`.
* **Entorno y configuración:** HOME y XDG_CONFIG_HOME temporales, distintos por escenario; configuración de red habilitada con lista de clientes vacía para separar filtrado de red de permisos de trabajos. Schedulers propios, un worker, un cupo de cola y puertos libres dinámicos. `HERMES_TEST_PORT` permite solicitar un puerto específico; se verifica que esté libre en cada escenario. El puerto por defecto 45820 se sustituye para no interferir con la instalación del operador.
* **Datos de entrada:** sobres JSON `ping` y `submit true`, direcciones de origen controladas con `socket.bind()`, IP individual y `/32`, CIDR con bits de host, reglas privadas/VPN válidas y listas inválidas.
* **Fuentes:** [guía de pruebas de red](../scripts/GUIA-PRUEBAS-RED.md), [RF-20](../../docs/technical-guide/2-Nucleo%20del%20proyecto/RF-20.restriccion-redes-direcciones.md), [RNF-12](../../docs/technical-guide/2-Nucleo%20del%20proyecto/RNF-12.no-escuchar-publicamente.md), [RNF-13](../../docs/technical-guide/2-Nucleo%20del%20proyecto/RNF-13.acceso-remoto-LAN-VPN.md), contexto de red y guía Windows/WSL de PC A/PC B.

##### Criterios de aceptación

Todos los criterios son **[local]**. El control de las reglas y del origen es necesario; ejecutar desde PC B a través del proxy no permite inferir qué IP ve Hermes ni modificar de forma aislada su política.

##### Pasos reproducibles

Desde la raíz del repositorio, en WSL de PC A:

```bash
make -C src/hermes hermes
bash verif/scripts/TC-011.sh
echo $?
```

Puerto opcional, siempre comprobado libre:

```bash
HERMES_TEST_PORT=45865 bash verif/scripts/TC-011.sh
```

* **Resultado esperado:** una línea `PASS Vn/ACn` por criterio, mensaje `PASS: RF-20 RNF-12 RNF-13 TC-011 sin fallos.` y código **0**. Código 1 indica aserción o limpieza fallida; 2 indica error de entorno. No hay criterios remotos ni omisiones requeridas: esta prueba no necesita código 3 ni participación de PC B.
* **Evidencia:** se agrega una sección por ejecución a `verif/results/results_TC-011.md` con fecha, commit, estado del árbol, configuración y puerto de cada escenario y resultados. No se sobrescriben intentos previos.

##### Alcance y decisiones

El caso sigue el contrato completo de la guía aunque use el número TC-011 solicitado. No cambia código de producción, configuración real, enlaces de desarrollo, proxy o firewall. Todos los servidores y schedulers se ejecutan bajo directorios temporales propios; la limpieza utiliza el `scheduler.lock` de cada entorno, nunca señales por nombre de proceso.

La prueba mantiene la escucha en `127.0.0.1` y enlaza explícitamente el origen de cada socket. No necesita escuchar en `0.0.0.0` para distinguir .1 de .2; el código actual rechaza esa interfaz y usa fallback seguro.

Los rechazos se verifican como EOF o RST sin datos de aplicación, no como un fallo obligatorio de `connect()`. Se exige evento con origen real y motivo, respetando la ventana de registro por motivo: no se exige un evento por cada conexión repetida.

AC5 valida aceptación de configuración privada/VPN; no simula tráfico proveniente de todas esas redes. El tráfico efectivo de pertenencia se verifica con orígenes loopback en AC2–AC4. La demostración LAN entre equipos está en TC-010; este caso no acredita un túnel VPN ni audita las reglas de Windows. En WSL NAT, las reglas operativas de Hermes deben utilizar el origen observado del proxy; el firewall de Windows limita los equipos exteriores.

Una interfaz inválida permite fallback a loopback; una interfaz privada válida pero no asignada produce fallo de bind. Una lista de redes inválida aborta el arranque, sin fallback permisivo. Estas respuestas distintas son parte del contrato y se prueban por separado.
