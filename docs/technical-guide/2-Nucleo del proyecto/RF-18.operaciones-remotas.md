# RF-18: Envío, consulta, listado y cancelación remotos

## Alcance

Un cliente registrado puede enviar trabajos al servidor principal, consultar su
estado y resultado, filtrar sus trabajos y solicitar su cancelación. El servidor
los procesa con su scheduler existente: concurrencia, cola, estados,
persistencia y recuperación son los locales. La distribución desde el servidor
hacia otros ejecutores, las sesiones persistentes y el control exclusivo de
clientes ejecutores siguen pendientes.

Por decisión explícita del usuario, el transporte actual es TCP con mensajes
JSON, sin certificados, TLS ni dependencia de OpenSSL. El cliente no necesita
`client.json`, claves, CA ni otros archivos de credenciales. Esta versión no
cifra el tráfico ni verifica criptográficamente la identidad de los equipos;
los permisos se asignan por la IP de origen observada por el servidor.
La propuesta de TLS del ADR queda pendiente para una entrega posterior.

## Configuración del servidor

La configuración general de RF-16 permanece en `~/.config/hermes/config.json`.
Para escuchar en LAN, usar la IPv4 real de la interfaz del servidor y autorizar
las direcciones de origen mediante RF-20. Ejemplo: servidor `192.168.1.20`,
cliente `192.168.1.25`:

```json
{
    "directorio_datos": "/home/usuario/.local/share/hermes/data",
    "trabajos_maximos": 5,
    "max_cola": 0,
    "interfaz": "192.168.1.20",
    "puerto": 45820,
    "redes_permitidas": ["127.0.0.0/8", "192.168.1.25"]
}
```

Conservar los valores existentes de directorio, concurrencia y cola al agregar
la configuración de escucha. Las IP del ejemplo deben reemplazarse por las
reales. `0.0.0.0` sigue siendo una opción explícita para escuchar en todas las
interfaces IPv4 y no amplía los permisos de origen por sí misma. El firewall,
NAT o una red virtual pueden requerir configuración externa para llegar al
puerto desde otro equipo.

La habilitación de trabajos remotos y los permisos se guardan por separado en
`~/.local/share/hermes/network/network.json`, independientemente del directorio
de datos configurable:

```json
{
    "habilitada": true,
    "clientes": [
        {
            "id": "pc-02",
            "direcciones": ["192.168.1.25"],
            "operaciones": ["submit", "query", "list", "cancel"],
            "programas": ["sleep", "true", "false", "/usr/bin/sleep"]
        }
    ]
}
```

La plantilla `src/hermes/examples/network/network.json` es funcional para una
prueba local con origen `127.0.0.1`. Copiarla al directorio de red y agregar el
cliente LAN con sus direcciones reales para usarla entre computadoras.

Sin `network.json`, o con `habilitada: false`, el servidor conserva el diagnóstico
`ping` y rechaza operaciones de trabajos con `UNAUTHORIZED`. Al habilitarlo,
valida el archivo completo antes de iniciar el scheduler o abrir el puerto.
Reiniciar el servicio después de modificar la configuración.

## Clientes y permisos

Cada registro contiene:

- `id`: nombre estable de administración, de 1 a 128 caracteres válidos para
  `request_id`. No es una identidad autenticada ni el UUID futuro del nodo.
- `direcciones`: una o varias IPv4 individuales privadas, loopback o de los
  espacios VPN admitidos en RNF-13. No admite hostnames ni rangos CIDR aquí.
- `operaciones`: subconjunto de `submit`, `query`, `list`, `cancel`.
- `programas`: nombres o rutas literales permitidos para enviar trabajos.

Una IP solo puede pertenecer a un registro. Los nombres de registro duplicados,
IPs repetidas, direcciones públicas y permisos desconocidos se rechazan antes
del arranque. La lista general `redes_permitidas` acepta CIDR como antes y sigue
siendo el primer filtro; el registro individual asigna los permisos de trabajos.
Un origen permitido por RF-20 pero sin registro puede hacer `ping`, pero no
administrar trabajos. El servidor nunca confía en una identidad enviada en JSON.

Si cambia la IP por DHCP, actualizar `direcciones` conservando `id`: se mantiene
el propietario del historial y el ámbito de deduplicación. Las direcciones LAN
y VPN del mismo equipo pueden asociarse al mismo registro. Si varios equipos
comparten una IP por NAT, el servidor no puede diferenciarlos en este modo.

Los programas se ejecutan con el usuario, PATH y directorio de trabajo del
servidor. Un nombre como `sleep` debe figurar como `sleep` en los permisos,
aunque también esté autorizada `/usr/bin/sleep`. Los argumentos se entregan
como una lista, sin concatenar comandos. Autorizar un intérprete permite el
código que ese intérprete admita; no se implementan sandbox ni reglas por
argumento en esta entrega.

## Semántica del CLI

Iniciar el servidor:

```sh
./hermes red start
```

Desde el otro equipo, con Hermes compilado y usando el nombre o IP del servidor:

```sh
./hermes red job 192.168.1.20 sleep 30
./hermes red job 192.168.1.20 --request-id solicitud.1 sleep 30
./hermes red filter 192.168.1.20 id 1
./hermes red filter 192.168.1.20 status RUNNING
./hermes red filter 192.168.1.20 programa sleep
./hermes red cancel 192.168.1.20 1
```

El cliente usa el puerto de su propia configuración RF-16, 45820 por defecto.
No necesita habilitar su servidor local ni registrar certificados. Los nombres
DNS se resuelven a IPv4 dentro de los espacios admitidos por RNF-13.

| Local | Remoto |
| --- | --- |
| `hermes job sleep 30` | `hermes red job <host> sleep 30` |
| `hermes job --request-id r.1 sleep 30` | `hermes red job <host> --request-id r.1 sleep 30` |
| `hermes filter id 1` | `hermes red filter <host> id 1` |
| `hermes filter status RUNNING` | `hermes red filter <host> status RUNNING` |
| `hermes filter programa sleep` | `hermes red filter <host> programa sleep` |
| `hermes cancel 1` | `hermes red cancel <host> 1` |

Los validadores, presentación y admisión son compartidos. `--request-id` es
opcional; sin él, cada invocación crea una solicitud nueva. Con él, repetir el
mismo ID, programa y argumentos devuelve el mismo trabajo dentro del registro
de cliente, incluso tras reiniciar. La deduplicación persiste mientras se
conserve el historial del job. Otro programa o argumentos con el mismo ID se
rechazan. Se permiten letras, dígitos, punto, dos puntos, guion y guion bajo,
con longitud entre 1 y 128 caracteres.

`job` muestra el ID y PID o espera en cola, con la misma espera breve de inicio
y tratamiento de duplicados y fallos que el CLI local. No espera a que termine
un trabajo largo ni retorna necesariamente el código final del programa.

Los filtros muestran todos los trabajos propios coincidentes; la paginación
es interna. `filter id` muestra estado, PID, programa, argumentos, tiempos,
código de salida y diagnóstico. No se transmite stdout, igual que en la
persistencia local. La ausencia de coincidencias se informa y retorna 0,
como en los filtros locales.

`cancel` reutiliza `cancelarJobDetallado` con comprobación atómica del propietario.
En cola marca CANCELED; en ejecución registra la solicitud y el supervisor
entrega SIGTERM, escalando a SIGKILL tras cinco segundos si hace falta. El worker
confirma la terminación. Se conserva la distinción local entre `Job cancelado`
y `Cancelación solicitada`, así como el rechazo de estados terminales.

Los trabajos locales y de otros registros no se exponen; se presentan como no
encontrados. La autenticación por certificado ya no se aplica: esta separación
depende exclusivamente de la dirección observada y del registro del servidor.

## Protocolo y persistencia

Se conserva RNF-08: JSON terminado en salto de línea, un mensaje por conexión,
16 KiB de entrada, 256 KiB de respuesta y plazos acotados de lectura/escritura.
Los nombres `query` y `list` solo se utilizan internamente, no son comandos CLI.

| operation | params |
| --- | --- |
| submit | `{"programa":"sleep","argumentos":["30"]}` |
| query | `{"job_id":1}` |
| list | `{"after":0,"limit":20,"tipo":"status","valor":"RUNNING"}` |
| cancel | `{"job_id":1}` |

`list` permite omitir el filtro para consultar todos los trabajos propios y
admite entre 1 y 50 elementos por página. Los errores incluyen `UNAUTHORIZED`,
`PROGRAM_NOT_ALLOWED`, `INVALID_PARAMS`, `NOT_FOUND`, `NOT_CANCELABLE`,
`JOB_OPERATION_FAILED` y `RESPONSE_TOO_LARGE`.

Los trabajos guardan `propietario_remoto: tcp-<id>` y `tipo_ejecucion: remote`
desde su creación atómica. Los IDs de solicitud persistidos incluyen ese ámbito.
No se editan archivos de otro equipo. Perder la conexión de una solicitud no
interrumpe un trabajo ya admitido en el servidor; no existe aún una sesión de
control hacia un ejecutor remoto.

Las configuraciones antiguas con `tls` o clientes `sha256` se rechazan con un
mensaje de migración. Reemplazarlas por registros con `id` y `direcciones`.
El historial de anteriores propietarios por certificado no se reasigna de forma
automática.

## Compilación y pruebas

No se requiere OpenSSL ni herramientas para certificados:

```sh
make -C src/hermes
python3 src/hermes/tests/network_remote.py
python3 src/hermes/tests/network_invalid.py
```

Las pruebas usan HOME y datos temporales y sockets TCP reales. Cubren ejecución,
consulta, filtros, cancelación, escalado de señales, permisos por IP/operación/
programa, aislamiento de propietarios, deduplicación, reinicio y conservación del
historial al agregar otra IP al mismo registro. Comparan salida y códigos de
retorno del CLI local y remoto; comprueban que el cliente no necesita credenciales.
Al terminar detienen los procesos y scheduler de la prueba.

## Validación manual entre dos equipos WSL y Windows

El usuario confirmó la conexión entre PC B y PC A después de corregir la IP
remota autorizada en el firewall de Windows. La configuración y el procedimiento
reproducible están en la [guía PC A / PC B](../../user-guide/red-wsl-pc-a-pc-b.md),
con JSON completos, proxy, reglas de firewall y pruebas por cada tramo.

| Parámetro | PC A, servidor | PC B, solicitante |
| --- | --- | --- |
| IPv4 LAN de Windows | `192.168.1.74` | `192.168.1.73` |
| IPv4 interna WSL | `172.25.70.19/20` | `172.23.236.91` |
| Gateway WSL | `172.25.64.1` | `172.23.224.1` |
| Puerto TCP | `45820` | Destino `192.168.1.74:45820` |

El proxy de Windows de A reenvía `192.168.1.74:45820` hacia
`172.25.70.19:45820`. La prueba Windows → WSL mostró origen `172.25.64.1` y
TCP True. Hermes registra ese origen en `redes_permitidas` y en el cliente
`pc-b-via-windows`; el firewall restringe el acceso exterior a `192.168.1.73`.
Esta separación es necesaria porque el proxy sustituye la conexión original:
Hermes no identifica directamente a B por su IP LAN en este recorrido.

### Incidente y resolución observados

PC B reportaba PingSucceeded False y TcpTestSucceeded False. En A se verificó
que Hermes escuchaba en `172.25.70.19:45820`, Windows alcanzaba ese puerto,
IP Helper estaba Running y el proxy escuchaba y respondía localmente en
`192.168.1.74:45820`. La regla de firewall era Allow e Inbound, pero contenía
`RemoteAddress: 192.168.1.7`. La IP correcta de B era `192.168.1.73`.

La corrección, desde PowerShell administrador de A, fue:

```powershell
Get-NetFirewallRule -Name "Hermes-PC-B-45820" |
    Get-NetFirewallAddressFilter |
    Set-NetFirewallAddressFilter -RemoteAddress 192.168.1.73
```

Luego se verificaron LocalAddress y RemoteAddress y se repitió desde B:

```powershell
Test-NetConnection 192.168.1.74 -Port 45820
```

El usuario confirmó que funcionó después de esta corrección. Esa confirmación
corresponde a la resolución del incidente de conectividad; los resultados de
cada trabajo se verifican con los comandos de envío, filtro y cancelación de
la guía, sin inferirlos únicamente de una prueba TCP exitosa.

La configuración persistente de Hermes es parte de RF-18; `portproxy`, IP Helper
y el firewall son preparación del entorno Windows/WSL. La existencia de una
regla de proxy o una prueba TCP positiva no prueban por sí solas la autorización
de operaciones de Hermes. Si DHCP cambia las direcciones, revisar cada capa
según la tabla de diagnóstico de la guía.
