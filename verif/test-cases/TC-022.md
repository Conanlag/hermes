# TC-022: Interrupción durante persistencia y recuperación fail-closed

**Requisitos cubiertos:** RNF-28, RNF-31, RNF-10, RNF-11, RNF-30
**Métodos de verificación:** Prueba
**Nivel de prueba:** Integración / robustez

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Comprobar que una terminación abrupta del daemon mientras persiste Jobs no deja `jobs.json` inutilizable y que Hermes conserva o recupera datos válidos mediante escritura atómica, respaldo `jobs.json.bak`, limpieza de temporales y restauración. Verificar además que, al reiniciar, los estados de Jobs se reconcilien de forma fail-closed: trabajos `RUNNING` obsoletos y estados desconocidos se clasifiquen como `INTERRUPTED` con motivo, sin reejecutar terminales ni señalizar procesos cuya identidad no sea verificable.
* **Precondiciones:** Linux con `/proc` montado y legible, incluyendo `/proc/sys/kernel/random/boot_id` y `/proc/<pid>/stat`; Bash; Perl con `JSON::PP`; y Hermes compilado y ejecutable. El usuario debe poder crear procesos y directorios temporales. Ejecutar desde el repositorio en un entorno controlado.
* **Entorno y configuración:** Clon limpio, compilación con GCC o Clang y `HOME` temporal aislado creado por el script. Hermes lee y escribe sus datos dentro de ese `HOME`; los Jobs e historial del usuario no se modifican. Se requiere `/proc` para observar identidad y ciclo de vida de procesos. No se requiere LAN ni VPN. El caso combina cierre ordenado (`SIGTERM`) con interrupción abrupta (`SIGKILL`) según cada escenario.
* **Datos de entrada:** Ráfaga de 40 Jobs breves durante escrituras concurrentes de `jobs.json`; señal `SIGKILL` al daemon durante la ráfaga; un temporal huérfano `jobs.json.tmp.999999.7`; corrupción controlada de `jobs.json` para ejercitar la restauración desde `jobs.json.bak`; y registros de prueba para estados `QUEUED`, terminales, estado desconocido y `RUNNING` sin PID verificable. Otros escenarios del script usan Jobs `sleep` para comprobar reconciliación y terminación de grupos.
* **Pasos reproducibles:**
  1. Desde la raíz del repositorio, compilar Hermes con `make -C src/hermes`.
  2. Ejecutar `bash verif/scripts/TC-022.sh`.
  3. Esperar la conclusión de los escenarios y comprobar el código de salida, la salida del script y `verif/results/results_TC-022.md`.
* **Resultado esperado:** El script termina con código `0` y muestra `PASS: TC-022`. En particular, después de `SIGKILL` durante la ráfaga, `jobs.json` y `jobs.json.bak` deben parsear como arreglos JSON; al iniciar la recuperación, el temporal huérfano debe limpiarse y `jobs.json` debe seguir siendo válido. Si `jobs.json` se corrompe deliberadamente pero el respaldo es válido, una lectura debe recuperar el registro terminal y reparar el archivo principal. Para RNF-31, los registros obsoletos o desconocidos deben clasificarse como `INTERRUPTED` con el motivo correspondiente, los Jobs `QUEUED` y terminales deben conservar la semántica definida y no deben inventarse terminaciones ni señalizarse procesos ajenos.

El caso de interrupción usa `SIGKILL` durante las escrituras; `hermes clean scheduler` realiza un cierre ordenado y no sirve para interrumpir una escritura en curso. El script también ejercita cierres ordenados con `SIGTERM` en los escenarios que requieren validar esa ruta.

La ráfaga aumenta la probabilidad de que el `SIGKILL` coincida con una escritura, pero no fuerza ni demuestra que la señal interrumpa una instrucción concreta de escritura. El criterio comprobado es que los archivos sigan íntegros o sean recuperables después de la caída; la prueba de respaldo se fuerza de manera determinista corrompiendo `jobs.json` con `jobs.json.bak` válido.
