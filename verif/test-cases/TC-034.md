# TC-034: Admisión remota sin espera bloqueante al scheduler

**Requisitos cubiertos:** RF-22 (AC5) y compatibilidad del contrato `submit`
**Métodos de verificación:** Prueba
**Nivel de prueba:** Rendimiento y funcional

#### 1. Fase de Diseño (Planificación)
* **Objetivo:** Verificar que `hermes red job` responde sin esperar al scheduler (Job en `QUEUED` con `pid: 0`), conserva el formato de admisión del cliente, mantiene la deduplicación por `request_id` y permite que el Job remoto termine correctamente.
* **Precondiciones:** Linux o WSL con Bash; Hermes compilado; puerto `45820` libre; `network.json` con `127.0.0.1` autorizado.
* **Entorno y configuración:** `HOME` temporal aislado; servidor y scheduler lanzados por el script; umbral de `1000 ms` para la respuesta de admisión.
* **Datos de entrada:** `hermes red job 127.0.0.1 true`; dos envíos con `--request-id v9-dup`; consulta posterior con `red filter 127.0.0.1 id <id>`.
* **Pasos reproducibles:**
  1. Compilar con `make -C src/hermes`.
  2. Ejecutar `bash verif/scripts/TC-034.sh`.
  3. Revisar el código de salida y `verif/results/results_TC-034.md`.
* **Resultado esperado:** La admisión responde en menos de 1000 ms con `job ID: N` y `PID: pendiente (en cola)`; el segundo envío con el mismo `request-id` informa `Solicitud duplicada`; el Job termina en `SUCCEEDED` y el servicio sigue vivo.

#### 2. Fase de Ejecución (Resultados empíricos)
* **Resultado observado:** Ejecución del 2026-11-18 en WSL Ubuntu con código `0`. La admisión respondió en `21 ms` con `PID: pendiente (en cola)`; el envío repetido informó `Solicitud duplicada`; el Job `1` alcanzó `SUCCEEDED` y el servicio permaneció activo.
* **Artefactos de evidencia:** `verif/scripts/TC-034.sh`; `verif/results/results_TC-034.md`.
