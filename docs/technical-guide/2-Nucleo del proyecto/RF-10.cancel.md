# RF-10 — Cancelación de trabajos

## Descripción

El requisito RF-10 permite al usuario solicitar la cancelación de un trabajo en cola o en ejecución, y refleja el resultado en el estado persistido. Es la primera operación de Hermes que combina escritura en disco con una señal del sistema: marca la intención en `jobs.json` y, cuando existe un proceso real, lo detiene con `SIGTERM`.

El diseño separa dos casos con naturalezas distintas. Un trabajo `QUEUED` aún no tiene proceso (`pid = 0`), así que se cancela de forma directa y síncrona marcando `CANCELED`. Un trabajo `RUNNING` ya tiene proceso y supervisor activos, así que la cancelación es asíncrona en dos pasos: se registra `cancel_requested` en disco y se envía la señal; el supervisor confirma despertando y persistiendo el estado final. Sin el flag, matar el proceso reportaría `FAILED`; sin la señal, el proceso seguiría corriendo.

El módulo `cancel` orquesta sin ser dueño de nada: reutiliza `actualizarResultadoJob` y `marcarCancelacionSolicitada` de `job`, `terminarProceso` de `process`, la validación de ID de RF-02 y la lectura tipada de RF-08.

---

## Objetivo

La meta técnica exacta es cancelar en ambos estados con mensajes que expliquen la causa de cada rechazo y sin romper a los consumidores existentes.

> El usuario deberá poder solicitar la cancelación de un trabajo en cola o en ejecución; el sistema deberá reflejar el resultado.

Consideraciones actuales:
- Hace: `QUEUED` → `CANCELED` directo con `codigo_salida = -1`, sin señal, mensaje `Job cancelado:`.
- Hace: `RUNNING` → registra flag + `SIGTERM`, mensaje `Cancelación solicitada:`, el supervisor persiste `CANCELED` con `codigo_salida = -SIGTERM`.
- Hace: rechazos con causa (`NO_EXISTE` → `No existe el Job ID:`, `NO_CANCELABLE` → `El Job no se puede cancelar (estado: X)...`, fallos de archivo/PID/señal con detalle) y `cancelarJob` original preservada como envoltorio.
- NO hace: cancelación de `SUCCEEDED`, `FAILED` o `CANCELED` (se rechazan con el estado actual).
- NO hace: `SIGKILL` ni reintentos: solo un `SIGTERM` por solicitud.
- NO hace: protección total contra la carrera `QUEUED → RUNNING` (el supervisor puede promover entre lectura y escritura; pendiente de equipo, ver integración).

## Definición de los estados

Reutiliza `Status` sin crear estados nuevos, más el veredicto propio de la operación:

```cpp
enum class CodigoCancelacion {
    CANCELADO,
    SOLICITUD_REGISTRADA,
    NO_EXISTE,
    NO_CANCELABLE,
    ERROR_LECTURA
};
```

| Código | Cuándo | Efecto en disco/proceso |
| ------ | ------ | ----------------------- |
| `CANCELADO` | Job `QUEUED` | `status = CANCELED`, `codigo_salida = -1`. Sin señal. Inmediato. |
| `SOLICITUD_REGISTRADA` | Job `RUNNING` con PID válido | `cancel_requested = true` + `SIGTERM`. El supervisor persiste `CANCELED`. |
| `NO_EXISTE` | ID ausente | Sin efectos. Mensaje `No existe el Job ID:`. |
| `NO_CANCELABLE` | `SUCCEEDED`, `FAILED` o `CANCELED` | Sin efectos. Mensaje con el estado actual. |
| `ERROR_LECTURA` | Archivo ilegible, JSON roto, estado/PID ilegible, señal fallida | Sin efectos garantizados. Mensaje con detalle. |

## Implementación de `.h`

**1. Propósito.** `cancel.h` promete dos sabores: el booleano histórico y el detallado con causa. Nada más.

**2. Dependencias.** Solo `<string>` para el mensaje del resultado. No incluye `job.h` ni JSON: el contrato no expone persistencia.

**3. Estructuras.**

```cpp
enum class CodigoCancelacion {
    CANCELADO,
    SOLICITUD_REGISTRADA,
    NO_EXISTE,
    NO_CANCELABLE,
    ERROR_LECTURA
};

struct ResultadoCancelacion {
    bool exito;
    CodigoCancelacion codigo;
    string mensaje;
};
```

**4. Prototipos.**

```cpp
bool cancelarJob(unsigned int jobId);
ResultadoCancelacion cancelarJobDetallado(unsigned int jobId);
```

Se mantuvo `cancelarJob` intacta como envoltorio (`return detallado.exito`) para no romper consumidores. La nueva función documenta en su comentario las cinco ramas.

## Implementación de `.cpp`

### Búsqueda y ramificación por estado

`cancelarJobDetallado` abre `jobs.json` con `ifstream`, parsea con `try/catch` genérico y recorre buscando `job_id`. Al encontrarlo exige `status` tipo string y ramifica:

```cpp
string estado = job["status"];

if (estado == "QUEUED") {
    if (actualizarResultadoJob(jobId, Status::CANCELED, -1)) {
        return {true, CodigoCancelacion::CANCELADO, ""};
    }
    return {false, CodigoCancelacion::ERROR_LECTURA, "No se pudo actualizar el Job."};
}

if (estado != "RUNNING") {
    return {false, CodigoCancelacion::NO_CANCELABLE, "El Job no se puede cancelar (estado: " + estado + "). Solo QUEUED o RUNNING."};
}
```

La rama `QUEUED` no pide PID ni señal: delega la atomicidad a `actualizarResultadoJob` (con `flock`). Cualquier otro estado no cancelable se rechaza citando el estado real, que es lo que hace útil el mensaje.

### Camino `RUNNING`: marca y señal

```cpp
int pid = job["pid"];  // acepta con o sin signo

if (!marcarCancelacionSolicitada(jobId)) {
    return {false, CodigoCancelacion::ERROR_LECTURA, "No se pudo registrar la cancelación."};
}

if (terminarProceso(pid)) {
    return {true, CodigoCancelacion::SOLICITUD_REGISTRADA, ""};
}

return {false, CodigoCancelacion::ERROR_LECTURA, "No se pudo enviar la señal al proceso."};
```

El orden importa: primero el flag en disco, después la señal. Si se invirtiera y la señal llegara antes de persistir el flag, el supervisor podría ver un proceso muerto sin marca y reportar `FAILED` en vez de `CANCELED`. `terminarProceso` es `kill(pid, SIGTERM)` con guarda `pid <= 0`.

### Cierre

Si el recorrido termina sin match: `{false, NO_EXISTE, "No existe el Job."}`. `main.cpp` lo traduce a `No existe el Job ID: <n>`.

## Integración con `main.cpp`, `job`, `process` y `validator`

`main.cpp` valida existencia (`argc < 3`) y contenido (`validarIdTexto`, RF-02) antes de convertir con `stoul` ya seguro, luego delega y traduce cada código:

```cpp
ResultadoCancelacion cr = cancelarJobDetallado(id);

if (!cr.exito) {
    if (cr.codigo == CodigoCancelacion::NO_EXISTE) {
        error("No existe el Job ID: ", id);
    } else if (cr.codigo == CodigoCancelacion::NO_CANCELABLE) {
        error(cr.mensaje);
    } else {
        error("No se pudo cancelar el Job: ", id, ". ", cr.mensaje);
    }
    return 1;
}

if (cr.codigo == CodigoCancelacion::CANCELADO) {
    info("Job cancelado: ", id);
} else {
    info("Cancelación solicitada para el Job: ", id);
}
```

Nota: `./hermes cancel <1>` sin comillas nunca llega al programa: `bash` interpreta `<` y `>` como redirección y falla con `syntax error`. Con comillas (`"<1>"`) sí llega y RF-02 lo rechaza como mal formado.

## Integración con RF-01, RF-02, RF-06 y RF-08

Culmina la cadena: RF-01 crea y persiste, RF-02 valida el ID de entrada, RF-06 provee el vocabulario de estados, RF-08 ofrece la lectura tipada que `main` usó transitoriamente para distinguir mensajes (reemplazada por el código directo del resultado). El supervisor de RF-01/RF-04 es quien confirma la rama `RUNNING` al despertar.

## Ejemplo de funcionamiento

**1. Cancelación en ejecución:**

```bash
./hermes job sleep 30
./hermes cancel 5
./hermes filter id 5
```

```text
job ID: 5
Cancelación solicitada para el Job: 5
Job ID: 5
PID: 1556
Programa: sleep
Estado: CANCELED
Codigo de salida: -15
Argumentos: 30
```

El `-15` es `-SIGTERM`: prueba de que el proceso murió por la señal y el supervisor persistió el estado.

**2. Cancelación en cola (ID 999 plantado como `QUEUED`, `pid 0`):**

```bash
./hermes cancel 999
./hermes filter id 999
```

```text
Job cancelado: 999
Job ID: 999
PID: 0
Programa: sleep
Estado: CANCELED
Codigo de salida: -1
Argumentos: 30
```

**3. Rechazos con causa:**

```bash
./hermes cancel 999999
./hermes cancel 1
```

```text
No existe el Job ID: 999999
El Job no se puede cancelar (estado: SUCCEEDED). Solo QUEUED o RUNNING.
```

`data/jobs.json` solo cambia en los dos casos exitosos: `CANCELED` con `cancel_requested` marcado.
