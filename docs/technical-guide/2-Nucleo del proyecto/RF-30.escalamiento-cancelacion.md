# RF-30 — Política de escalamiento de cancelación

## Descripción

RF-30 define cómo Hermes intenta terminar un proceso asociado a un Job cuando la cancelación se solicita y su PID ya está disponible. La política comienza con una señal cooperativa `SIGTERM`, da al proceso hasta cinco segundos para desaparecer y, si todavía existe, intenta terminarlo con `SIGKILL`.

La secuencia se implementa en `escalarCancelacionProceso` dentro de `process.cpp`. El CLI la invoca desde la cancelación de un Job `RUNNING` con PID positivo. El trabajador conserva la responsabilidad de recolectar el proceso con `waitpid` y de persistir el estado y código de salida; la función de escalamiento no espera al hijo ni decide por sí misma el estado final.

Si una cancelación encuentra el Job `RUNNING` pero todavía con PID `0`, esta ruta no se ejecuta. El scheduler enviará `SIGTERM` al proceso al guardar su PID, pero no inicia la espera ni el escalamiento a `SIGKILL` desde ese camino.

---

## Objetivo

Permitir que un proceso que no termina tras una solicitud normal de cancelación reciba una señal forzada, con un periodo de gracia limitado y sin trasladar a la función de cancelación la responsabilidad de recolectar al hijo.

Consideraciones actuales:
- Hace: valida que el PID sea positivo y el tiempo de gracia no sea negativo.
- Hace: intenta `SIGTERM` primero.
- Hace: comprueba la existencia del PID cada 100 ms durante el periodo de gracia.
- Hace: intenta `SIGKILL` si el PID sigue existiendo al terminar la espera.
- Hace: considera `ESRCH` como que el proceso ya no existe, sin enviar otra señal.
- Hace: devuelve error si una señal falla por una causa distinta de `ESRCH`.
- NO hace: configurar el tiempo desde CLI o archivo de configuración; `cancel.cpp` usa cinco segundos.
- NO hace: recolectar al hijo ni esperar a que el proceso muera después de `SIGKILL`; eso sigue a cargo del trabajador.
- NO hace: escalar desde el caso de PID `0`; el scheduler solo envía `SIGTERM` cuando guarda ese PID.

## Definición de los estados

RF-30 no incorpora estados nuevos al ciclo de vida del Job:

| Fase | Acción | Resultado de la función |
| ---- | ------ | ----------------------- |
| Validación | Rechaza `pid <= 0` o tiempo de gracia negativo | `false`, sin señal |
| Solicitud inicial | Envía `SIGTERM` | Continúa si se envió o si el PID ya no existe; error para otros fallos |
| Periodo de gracia | Consulta `kill(pid, 0)` cada 100 ms hasta completar el tiempo configurado | Éxito si `errno == ESRCH` |
| Escalamiento | Si aún existe, intenta `SIGKILL` | `true` si se envió o el proceso ya no existe; `false` ante otro error |
| Finalización | El trabajador recoge con `waitpid` y guarda el estado | `CANCELED` si existe `cancel_requested`; código de salida derivado del proceso |

Un retorno `true` después de `SIGKILL` confirma que la señal se envió (o que el PID ya había desaparecido); no confirma que el trabajador haya recolectado y persistido el resultado.

## Implementación de `.h`

El contrato público en `process.h` es:

```cpp
bool escalarCancelacionProceso(
    pid_t pid,
    int tiempoGraciaSegundos = 5
);
```

El argumento de gracia tiene un valor por defecto de cinco segundos. El llamador de cancelación también pasa `5` explícitamente. La función no modifica el contrato de `esperarProceso`, que sigue siendo responsabilidad del trabajador.

---

## Implementación de `.cpp`

El algoritmo en `process.cpp` sigue la secuencia:

```cpp
if (pid <= 0 || tiempoGraciaSegundos < 0) {
    return false;
}

if (kill(pid, SIGTERM) == -1 && errno != ESRCH) {
    return false;
}

// Consultar kill(pid, 0) cada 100 ms durante la gracia.
// Si sigue existiendo al terminar, intentar SIGKILL.
```

El bucle realiza diez comprobaciones por segundo. Con la invocación actual de cinco segundos, el máximo es cincuenta intervalos de 100 ms. `kill(pid, 0)` no envía una señal: se usa para consultar si el proceso existe y si puede ser señalado. Si ya no existe (`ESRCH`), el proceso de escalamiento termina con éxito sin enviar `SIGKILL`.

La función no llama `waitpid`: una vez que el proceso termina, el trabajador termina la lectura del pipe, recoge el estado de salida y persiste la terminación.

## Integración con `cancel`, `scheduler` y `storage`

`cancelarJobDetallado` registra `cancel_requested` bajo el bloqueo de almacenamiento antes de invocar el escalamiento. Solo invoca `escalarCancelacionProceso(pid, 5)` cuando el Job estaba `RUNNING` y el PID leído era positivo. Un error de señalización se devuelve como fallo de cancelación con el mensaje `No se pudo completar la solicitud de cancelación.`

El scheduler es el único que recolecta los procesos ejecutados por sus trabajadores. Al persistir el resultado, consulta `cancel_requested`: si la marca está activa, guarda `CANCELED`; el código de salida refleja cómo terminó el proceso, por ejemplo, `-15` si terminó por `SIGTERM` o `-9` si terminó por `SIGKILL`.

## Integración con RF-10, RF-26 y RF-06

- RF-10 presenta la solicitud al usuario y distingue cancelación inmediata en cola de solicitud a un proceso en ejecución.
- RF-26 mantiene coherentes las escrituras concurrentes del Job y la marca `cancel_requested`.
- RF-06 conserva los estados conocidos; el escalamiento no añade un estado `CANCELING`.

## Ejemplo de funcionamiento

El siguiente programa ignora `SIGTERM` y permanece activo hasta que recibe una señal que no puede ignorar, como `SIGKILL`:

```python
# ignorar_sigterm.py
import signal
import time

signal.signal(signal.SIGTERM, signal.SIG_IGN)
print("SIGTERM ignorada; esperando SIGKILL", flush=True)

while True:
    time.sleep(1)
```

Guarda el script como `ignorar_sigterm.py`, inicia el Job y solicita su cancelación cuando Hermes haya devuelto el ID:

```bash
./hermes job python3 ignorar_sigterm.py
./hermes cancel <ID>
./hermes filter id <ID>
```

Como el proceso ignora `SIGTERM`, seguirá activo durante el periodo de gracia. Aproximadamente cinco segundos después, Hermes intentará enviar `SIGKILL`. Una vez que el scheduler lo recolecte, la consulta debe reflejar la cancelación y el código de salida asociado a esa señal:

```text
Cancelación solicitada para el Job: <ID>
Estado: CANCELED
Codigo de salida: -9
```

La respuesta de `cancel` confirma el registro de la solicitud y el resultado de la operación de señales; el estado final aparece después de que el scheduler recolecta el proceso.
