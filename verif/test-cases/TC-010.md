# TC-010: Flujo remoto completo en LAN/VPN

**Requisitos cubiertos:** RF-18, RF-19 y RNF-26.
**Métodos de verificación:** Prueba y revisión de configuración.
**Nivel de prueba:** Integración y sistema, funcional y robustez.
**Modo previsto:** ambos (local autocontenido y remoto entre equipos).

#### 1. Fase de Diseño (Planificación)

* **Objetivo:** Verificar envío, consulta, listado y cancelación mediante Hermes Red, su equivalencia con las operaciones locales y su funcionamiento entre equipos por una LAN privada o VPN, teniendo en cuenta el recorrido Windows/WSL.
* **Precondiciones:** Linux o WSL con Bash, Python 3, `ss` y las herramientas indicadas en la guía; Hermes compilado en los equipos participantes; ejecución como usuario sin privilegios. Para la variante remota, PC A debe tener servidor y scheduler activos, capacidad disponible y permisos `submit`, `query`, `list`, `cancel` para el origen observado, con los programas literales `true`, `false` y `sleep` autorizados.
* **Entorno y configuración:** `HOME` y `XDG_CONFIG_HOME` temporales en cada ejecución. Modo local con servidor, scheduler, datos y puerto propios. Modo remoto con cliente temporal en PC B y destino proporcionado por el operador; no se administra el servidor ajeno.
* **Datos de entrada:** trabajos `true`, `false` y `sleep 120`; identificadores de solicitud únicos por ejecución y prefijados con `tc010`; IDs de trabajo obtenidos de cada respuesta, sin asumir que empiezan en 1.

El script está implementado y la variante local se ejecutó satisfactoriamente con código 3 (PASS parcial). Falta la ejecución real entre PC B y PC A; redactar o ejecutar solo la variante local no cierra el recorrido LAN/VPN.

##### Decisiones tras contrastar documentación y código

1. Se conserva el número **TC-010**, solicitado expresamente; no se renumeran casos. Aunque la guía describe los casos nuevos desde TC-057, se aplica su contrato completo a este caso nuevo.
2. El servidor ejecuta los trabajos en PC A. PC B utiliza el CLI y no necesita servidor, certificados ni TLS. No se comprueba transmisión de stdout/stderr porque no forma parte de la implementación remota actual.
3. La interfaz y el puerto proceden de `config.json`; los campos informativos `servidor` y `equipos` de `network.json` no controlan la escucha ni asignan identidades adicionales.
4. El puerto del cliente también procede de su `config.json`: `HERMES_TEST_PORT` debe escribirse en la configuración temporal, no pasarse como argumento adicional al CLI.
5. RNF-26 y `access.cpp` rechazan `0.0.0.0` y direcciones públicas. No se seguirá la variante de §3.8 de la guía que propone escuchar en `0.0.0.0`, ni las descripciones históricas de excepciones públicas `/32` del contexto. Se utilizará una IPv4 explícita permitida.
6. Las referencias antiguas a un único mensaje por conexión y a una espera de arranque del trabajo dentro de `submit` no serán aserciones del caso: RNF-24 admite solicitudes secuenciales y `remote.cpp` persiste el trabajo sin esperar su ejecución. Se consultará el estado final con un plazo acotado.
7. Un PASS en loopback verifica el flujo funcional local, pero no acredita una LAN o VPN. La variante entre equipos debe identificar el recorrido realmente usado; una prueba LAN no se presentará como una prueba de túnel VPN.

##### Preparación específica de WSL

En WSL NAT, el recorrido previsto es:

```text
PC B -> IP LAN privada de Windows A:puerto externo
     -> portproxy de Windows A
     -> IP interna de WSL A:puerto Hermes -> scheduler de A
```

Las IP de la guía son ejemplos históricos, no valores actuales garantizados. Antes de la ejecución real se deben confirmar IP LAN/VPN de destino, IP de WSL A, puerto externo, puerto interno y origen que Windows utiliza hacia WSL.

- En PC A, `redes_permitidas` y `clientes[].direcciones` autorizan el origen observado del proxy, normalmente el gateway de WSL A; no se sustituye por la IP de WSL de PC B.
- El firewall de Windows restringe el puerto de entrada a la IP real de PC B. Varios equipos detrás del proxy comparten el ámbito de acceso de Hermes; `HERMES_TEST_CLIENT_ID` es una etiqueta y no modifica ni autentica ese ámbito.
- El operador comprueba WSL A con `ss`, Windows A -> WSL A con `Test-NetConnection`, escucha y destino de `portproxy`, e ingreso desde Windows B. Un TCP positivo prepara la prueba; no acredita las operaciones de Hermes.
- Si Windows alcanza WSL pero falla la entrada LAN, revisar proxy e IP Helper según la guía. El script no reinicia servicios ni modifica firewall, proxy o `.wslconfig`.
- En VPN o WSL con acceso directo, documentar la interfaz y ruta reales. El destino debe pertenecer a RFC1918 o `100.64.0.0/10`; no se presupone que utilice portproxy.

|---|---|---|---|
| AC1 | ambos | Preparar configuración temporal, validar destino y comprobar `ping` JSON | Respuesta `pong` válida; versión e ID correlacionados; un ping por sí solo no aprueba el caso |
| AC2 | ambos | Enviar `true`, obtener su ID y consultar hasta estado terminal | `SUCCEEDED`, código 0; programa, argumentos y tiempos coherentes |
| AC3 | ambos | Enviar `false` y consultar su resultado | `FAILED`, código 1; se distingue admisión exitosa del resultado del programa |
| AC4 | ambos | Enviar `sleep 120`, esperar `RUNNING` y filtrar por ID, estado y programa | El ID propio figura en los filtros pertinentes, sin exigir que sea el único del historial |
| AC5 | ambos | Reenviar el mismo request ID, programa y argumentos | Mismo job ID y mensaje de duplicado, sin crear otro trabajo; cambiar argumentos con el mismo ID produce rechazo |
| AC6 | ambos | Cancelar el trabajo RUNNING y volver a consultar | Solicitud aceptada y posterior `CANCELED`; nueva cancelación terminal rechazada con `NOT_CANCELABLE` |
| AC7 | local | Repetir éxito, fallo, deduplicación, filtros y cancelación mediante CLI local | Mismos estados finales, códigos del programa y reglas de transición que en remoto; no se exige igualdad de IDs, PID o marcas de tiempo |
| AC8 | local | Con un worker ocupado y cupos de espera propios, cancelar un trabajo QUEUED por cada interfaz | Ambos terminan `CANCELED` sin iniciar su programa; no se fuerza saturación en PC A ajeno |
| AC9 | local | Contrastar respuestas con `jobs.json` y eventos relacionados | JSON íntegro; propietario `tcp-<ambito>` y tipo `remote` en trabajos remotos; IDs únicos y sin duplicación de la solicitud; eventos correlacionados de creación y transiciones |
| AC10 | local | Comprobar política privada con configuraciones aisladas | Una dirección pública en `network.json` impide el arranque; una interfaz inválida nunca abre escucha pública o comodín; el cliente no usa un destino público. Se distingue rechazo de fallback seguro a loopback |
| AC11 | remoto | Ejecutar el flujo desde PC B a PC A por LAN privada o VPN | Operaciones reales de Hermes completadas por la ruta documentada, no solo establecimiento TCP ni acceso desde el mismo equipo |
| AC12 | local | Detener únicamente los procesos propios y comprobar recursos | Cierre normal del servidor, scheduler detenido, puerto liberado y ausencia de procesos de la prueba |

En AC10 no se intenta conectar a Internet: las comprobaciones negativas deben quedar limitadas a validación y configuración local. El caso reutiliza las coberturas existentes de RNF-26 como referencia y no amplía la política de producción para facilitar la prueba.

##### Plan del script `verif/scripts/TC-010.sh`

1. Validar dependencias, binario, host, puerto y `HERMES_TEST_CLIENT_ID`; crear identificadores únicos. Usar `set -euo pipefail`, `umask 077` y límites de tiempo explícitos para invocaciones, consultas y limpieza.
2. Exportar `HOME` y `XDG_CONFIG_HOME` temporales. Registrar fecha, commit, modo, destino y etiqueta del cliente en evidencia append, sin secretos; indicar también si el árbol probado tiene cambios locales.
3. Detectar modo según la guía: `localhost` o `127.0.0.1` implica local; otro destino IPv4 permitido implica remoto y exige `HERMES_TEST_PORT`.
4. En local, elegir puerto libre con `bind(0)` o validar el solicitado, generar configuración y permisos propios, arrancar el servidor y esperar proceso vivo, mensaje de escucha y puerto LISTEN. Reintentar como máximo tres veces al elegir puerto automático. Crear un entorno separado para el dominio local de referencia, evitando interferencias de capacidad entre ambas interfaces.
5. Ejecutar AC1–AC6 usando el CLI real; complementar con sobres JSON para aserciones estructuradas. Capturar la admisión con `job ID:` y los detalles con `Job ID:`. Un retorno 0 de `filter id` sin bloque de trabajo no acredita existencia.
6. Consultar estados con espera activa y plazo acotado. Para cancelar en ejecución, observar primero `RUNNING`; no aceptar `QUEUED` como evidencia de cancelación RUNNING. En remoto se requiere capacidad disponible y no se cambia la concurrencia del servidor.
7. En local, ejecutar AC7–AC10 y recoger evidencia persistida. En remoto, ejecutar AC11 y emitir `SKIP` explícito para comprobaciones de archivos, comparación local en PC A, señales, permisos y recursos del servidor que el cliente no puede inspeccionar.
8. Registrar todos los IDs creados. La limpieza remota solo podrá solicitar por protocolo la cancelación de los trabajos de esta ejecución que sigan activos y verificar su estado; no enviará señales a PC A ni borrará su historial. Un fallo de limpieza de trabajos propios impide PASS.
9. Mediante `trap cleanup EXIT`, cerrar clientes y procesos locales propios, recoger al servidor con `wait`, localizar el scheduler por su archivo aislado, verificar puerto y procesos remanentes, cerrar la cerca Markdown y eliminar temporales. Conservar el código original salvo fallo de limpieza.
10. Imprimir una línea `PASS Vn/ACn` por comprobación y conservar `FAIL`, `SKIP` y errores de entorno en el historial. No modificar archivos de `src/` ni enlaces de desarrollo.

##### Pasos reproducibles previstos

Desde la raíz del repositorio:

```bash
make -C src/hermes hermes

# Integración autocontenida; puerto libre automático.
bash verif/scripts/TC-010.sh

# Desde WSL de PC B; reemplazar IP y puerto por los confirmados del entorno.
HERMES_TEST_HOST=192.168.1.83 HERMES_TEST_PORT=45820 \
  HERMES_TEST_CLIENT_ID=PC-B bash verif/scripts/TC-010.sh
```

`HERMES_TEST_PORT` en remoto representa el puerto visible desde PC B. Si el proxy traduce puertos distintos, se documentarán ambos: externo para el cliente e interno para la escucha de Hermes.

1. En ambos equipos, disponer de la misma versión del proyecto y compilar con `make -C src/hermes hermes`. Copiar también el script nuevo a PC B si todavía no está publicado en la rama descargada.
2. En WSL de A, ejecutar `./src/hermes/hermes red setup`. Confirmar modo NAT y las tres direcciones de A de la tabla. Registrar el equipo `PC-B` con IP LAN `192.168.1.81`; revisar los cambios antes de guardar y aplicar el PowerShell propuesto para proxy/firewall. La regla externa debe restringir el acceso a B; el origen autorizado en Hermes es `172.25.64.1`.
3. Comprobar en el resumen de setup el puerto real. Los comandos de esta ficha usan `45820`; si la instalación tiene otro, adaptar tanto el diagnóstico como `HERMES_TEST_PORT`. Los programas `true`, `false`, `sleep` y las cuatro operaciones deben estar permitidos; setup conserva los permisos de registros existentes.
4. En WSL de A, iniciar `./src/hermes/hermes red start` y mantener la terminal abierta. Debe indicar `172.25.70.19:45820`. Si existía otra instancia, detenerla con Ctrl+C y reiniciarla para cargar los cambios.
5. En PowerShell de A, comprobar `Test-NetConnection 172.25.70.19 -Port 45820`. En PowerShell de B, comprobar `Test-NetConnection 192.168.1.83 -Port 45820`. Ambos deben mostrar `TcpTestSucceeded: True`; si fallan, diagnosticar según la guía WSL antes de atribuir un fallo al requisito.
6. En WSL de B, ejecutar la variante remota indicada arriba. PC B no necesita `red start` ni `red setup`. El script crea su configuración temporal con el puerto indicado.
7. Conservar y compartir el archivo `verif/results/results_TC-010.md` de PC B. Junto con la evidencia local de A permitirá revisar todos los criterios y decidir el cierre. El código 3 es el resultado esperado cuando pasan los criterios de un modo y faltan los del otro.

##### Resultado esperado y reglas de cierre

- Código **0**: todas las comprobaciones aplicables se realizaron sin omisiones requeridas. En este caso dual, cada modo deja criterios exclusivos del otro pendientes, por lo que las ejecuciones aisladas normalmente son parciales.
- Código **1**: aserción incumplida o fallo de limpieza.
- Código **2**: error de entorno, como binario ausente, puerto solicitado ocupado, destino inválido/inalcanzable o falta de puerto remoto.
- Código **3**: comprobaciones realizadas correctas con criterios requeridos `SKIP` por el modo. Se registra cobertura parcial, sin convertir las omisiones en PASS.

El cierre completo de TC-010 requiere revisar conjuntamente las evidencias local y entre equipos: cada AC debe tener un resultado observado. El recorrido LAN/VPN permanece pendiente hasta una ejecución real desde otro equipo. Una pasada LAN permite cerrar esa alternativa del título «LAN/VPN»; no acredita además VPN. Se conserva la evidencia previa de RF-19 y RNF-26 sin atribuirla a este caso nuevo ni sustituirla por un PASS de planificación.
